Inverted Index and Boolean Queries

Overview of the lab

Goal: build an inverted index for a collection of documents and answer Boolean queries with it. The lab goes with the lectures on Boolean retrieval and on the dictionary and postings (IIR, chapters 1–2).

  1. The task: Boolean retrieval: what we build, why, and the indexing pipeline.
  2. Incidence matrices: the simplest index, on 14 news headlines.
  3. The inverted index: keep only the non-zero entries, as a dictionary and postings.
  4. From text to terms: tokenization, normalization, stop words, stemming.
  5. Dataset and the dictionary part: newsgroup posts, preprocess_document, document frequency.
  6. Building the full index: pairs, sort, merge, split.
  7. Boolean queries in the index: answering queries by merging postings lists.
  8. Faster query processing: term order by frequency, skip pointers.
  9. Phrase and proximity queries: biword and positional indexes.

The task: Boolean retrieval

Given a large collection of documents and a query such as wedding AND kills, return every document that satisfies the query.

  • Document: the unit we index and return. In this lab, first one news headline, later one newsgroup post. What counts as a document (a file? an e-mail? an e-mail with its 5 attachments?) is a design decision.
  • Collection (corpus): all the documents we search.
  • Boolean query: terms combined with AND, OR and NOT. The answer is a set of documents: each document matches or it does not, there is no ranking.
  • Why not just scan the text? Searching every document for every query (like grep) costs time proportional to the whole collection, again for each query. Instead we build an index once, in advance; a query then reads only the small part of the index about its own terms.

📐 Token and term

A token is one occurrence of a character sequence in a document (Friends). A term is the normalized form stored in the dictionary (friend). Every token is a candidate for an index entry, after the linguistic modules have processed it.

The lab builds the pipeline twice: first a toy version on 14 news headlines, to see the idea (incidence matrix, then inverted index); then a real one on newsgroup posts (dictionary, postings, queries).

Foundation

Incidence matrices

The simplest possible index: for every term and every document, record whether the term occurs in the document. Our toy collection is 14 BBC News headlines, one document each. Four steps turn them into this table, an incidence matrix: the tokenizer and one linguistic module (lower-casing) of the pipeline, then counting.

  1. Tokenize: split each sentence with NLTK's TweetTokenizer. Punctuation marks become tokens of their own: Istanbul. → Istanbul .
  2. Lower-case: The (doc 11) and the (docs 1, 13) become the same term the.
  3. Unique tokens: flatten the lists with sum(…, []) and put them in a set: 83 terms.
  4. Incidence matrix: one row per term, one column per document → shape (83, 14).

📐 Term-document incidence matrix

A matrix with one row per term \(t\) and one column per document \(d\). Entry \((t, d)\) is 1 if \(t\) occurs in \(d\) and 0 otherwise. The notebook stores the count sent.count(token) (term-document frequency), so the and in get a 2 in document 1.

Try it: answer a Boolean query with the matrix

Each term's row is a bit vector over the 14 documents. A Boolean query is a bitwise operation on rows: AND, OR, AND NOT. Rows are sorted alphabetically (a Python set has no fixed order).

💡 The matrix has \(83 \times 14 = 1{,}162\) cells but only 93 are non-zero (8%). With a real collection (millions of documents, hundreds of thousands of terms) almost every cell is 0, so storing the full matrix is wasteful. We store only the non-zero entries: that is the inverted index.

Data structure

The inverted index

For every term, keep only the documents it occurs in: only the non-zero cells of its row. The index is called inverted because it turns the natural view around: a document is a list of terms; the index stores, for each term, the list of documents. It has two parts.

  • Dictionary: the vocabulary of terms, each with its document frequency \(df_t\), the number of documents that contain \(t\).
  • Postings: for each term, the list of document ids that contain it (optionally with the term frequency in each). One entry is a posting.
  • ❗ Postings lists are kept sorted by document id; the query algorithms below rely on it.
  • Postings are usually implemented as linked lists (or variable-length arrays), because they grow as documents are added.

Lecture

From text to terms: tokenization and normalization

These are the tokenizer and linguistic-module stages of the pipeline: they decide which terms end up in the dictionary. The headlines used two choices (TweetTokenizer and lower-casing); here are the options the lecture discusses.

Tokenization

Splitting at spaces and punctuation is a start, but many cases are unclear. The last column is what the notebook's TweetTokenizer does with the lecture's examples.

  • Numbers and codes are often not indexed as text, but they can be very useful (think of looking up an error code). Meta-data such as creation date and format is often indexed separately.
  • Language: tokenization is language-specific. German noun compounds are not segmented (Lebens­versicherungs­gesellschafts­angestellter, 'life insurance company employee'); Chinese and Japanese have no spaces between words; Arabic and Hebrew are written right to left, with numbers left to right.
  • Parsing comes first: the format (pdf, Word, html), language and character set of each document must be detected, and one document can mix several (a French e-mail with a German pdf attachment).

Normalization

Terms in the documents and terms in the query must be put into the same form, so that U.S.A. matches USA.

  • Equivalence classes: the usual, implicit way, e.g. delete periods, so U.S.A. and USA become one term.
  • Asymmetric expansion: expand the query instead. Query window → search window, windows; windows → Windows, windows; Windows → Windows. More powerful, but less efficient.
  • Accents: résumé vs resume, Tuebingen vs Tübingen. What matters is how users type their queries, and they often leave accents out.
  • Case folding: lower-case everything. There are exceptions (General Motors, Fed vs fed, SAIL vs sail), but lower-casing everything is often best, since users type lower case anyway. In our headlines it turns the country US into us.
  • Thesauri and soundex: hand-built equivalence classes (car = automobile, color = colour), applied when indexing or by expanding the query; soundex expands names into phonetic variants (chebyshev → tchebycheff).

Stop words

A stop list removes the most common words from the dictionary entirely.

  • For: they carry little meaning (the, a, and, to, be) and take a lot of space: about 30% of the postings belong to the 30 most common words. In sci.crypt the occurs in 97 of the 100 posts, of and to in 92.
  • Against: some queries need them: phrases ("King of Denmark"), titles ("Let it be", "To be or not to be"), relations (flights to London). With good compression and query optimization, keeping them costs little.
  • The trend is away from stop lists: from 200–300 words, to 7–12, to none. Web search engines generally do not use them.

Lemmatization and stemming

  • Lemmatization: reduce inflected forms to the dictionary headword: am, are, is → be; car, cars, car's, cars' → car.
  • Stemming: crude chopping of affixes, language dependent. The lecture's example of the idea: automate(s), automatic, automation → automat.
  • Porter's algorithm: the commonest stemmer for English. Five phases applied one after the other; within a phase, the rule with the longest matching suffix is applied. Typical rules: sses → ss, ies → i, ational → ate, tional → tion. Some rules check the stem's length (its measure \(m\)): (m>1) ement → turns replacement into replac but leaves cement alone.
  • Does it help? Results are mixed: stemming and other normalizations help recall for some queries and hurt precision for others.

Dictionary

Dataset and the dictionary part (term and #docs)

Now the real collection: Usenet posts from the Twenty Newsgroups dataset. We build the index in two passes: first only the dictionary, each term with the number of documents that contain it; then, in the next section, the postings.

  • 20 Newsgroups: 20,000 messages from 20 newsgroups (UCI, donated in 1999 by Tom Mitchell).
  • mini_newsgroups: the smaller version we use, one folder per newsgroup with 100 messages each (e.g. sci.crypt, sci.electronics, rec.autos).
  • Each file is a whole post, headers included (Path, From, Subject, Message-ID, …).

Preprocessing a document

preprocess_document is our tokenizer and linguistic modules in one function. It returns the lower-cased tokens of a document, without punctuation: split into sentences (sent_tokenize), tokenize each sentence, drop punctuation, lower-case.

Document frequency

prepare_dataset preprocesses every file in a folder. document_frequency counts, for each token, the number of documents containing it: iterate over set(document), so a token counts once per document.

  • Why document frequency? It is stored in the dictionary next to each term, and it equals the length of the term's postings list. Queries use it to decide in which order to process terms (Faster query processing); ranked retrieval later uses it to give rare terms more weight.
document_frequency.py Python ▾ 
import os
from collections import defaultdict, Counter
from string import punctuation
from nltk.tokenize import sent_tokenize, TweetTokenizer

tokenizer = TweetTokenizer()

def preprocess_document(content):
    """
    Returns a list of tokens for a document's content.
    Tokens should not contain punctuation and should be lower-cased.
    """
    sentences = sent_tokenize(content)
    tokens = []
    for _sent in sentences:
        sent_tokens = tokenizer.tokenize(_sent)
        sent_tokens = [_tok.lower() for _tok in sent_tokens if _tok not in punctuation]
        tokens += sent_tokens
    return tokens

def prepare_dataset(documents_dir):
    """
    Returns list of documents in the documents_dir, where each document is a list of its tokens.
    """
    tokenized_documents = []
    for document in os.listdir(documents_dir):
        with open(os.path.join(documents_dir, document), errors='ignore') as outf:
            tokenized_documents.append(preprocess_document(outf.read()))
    print("Found documents: ", len(tokenized_documents))
    return tokenized_documents

def document_frequency(tokenized_documents):
    """
    Returns a dictionary {token: number of documents containing the token}
    """
    doc_freq = defaultdict(lambda: 0)
    for _document in tokenized_documents:
        for _token in set(_document):
            doc_freq[_token] += 1
    return doc_freq

print(preprocess_document("US wedding limousine crash kills 20. Kanye West, deletes social media profiles!"))
# ['us', 'wedding', 'limousine', 'crash', 'kills', '20', 'kanye', 'west', 'deletes', 'social', 'media', 'profiles']

tokenized_dataset = prepare_dataset('data/mini_newsgroups/sci.crypt/')   # Found documents:  100
df = document_frequency(tokenized_dataset)
print(Counter(df).most_common(10))
# [('path', 100), ('sci.crypt', 100), ('apr', 100), ('cantaloupe.srv.cs.cmu.edu', 100), ('message-id', 100),
#  ('date', 100), ('from', 100), ('subject', 100), ('newsgroups', 100), ('lines', 99)]

Index construction

Building the full index: pairs, sort, merge, split

Now the postings too. The key step of index construction is sorting: it brings all occurrences of a term together, so that its postings list can be written out in one go. Four steps turn a folder of documents into a dictionary and postings lists (the indexer stage of the pipeline).

  1. Extract pairs of (token, document_id): walk through every document and emit one pair per token. Also keep a map doc_id → file name.
  2. Sort by token: sorted(token_docid, key=itemgetter(0)). Python's sort is stable, and the pairs were produced in document order, so within each token the document ids stay ascending.
  3. Merge token occurrences in a single document: equal neighbours (token, doc_id) collapse into (token, doc_id, term_freq).
  4. Split into dictionary and postings: dictionary term → (doc_freq, total_freq), postings term → [(doc_id, term_freq), …]. total_freq is how often the term occurs in the whole collection; the term frequency in each document is kept because ranked retrieval will need it.

💡 This sorts everything in memory. For collections that do not fit in memory, the same sort is done block by block on disk (IIR, chapter 4).

build_index.py Python ▾ 
import os
from operator import itemgetter
from collections import defaultdict

def get_token_doc_id_pairs(category_dir):
    """
    Iteratively goes through the documents in the category_dir and constructs/returns:
    1. A list of (token, doc_id) tuples
    2. A dictionary of doc_id:doc_name
    """
    tkn_docid = []
    docid_docnm = {}
    for i, document in enumerate(os.listdir(category_dir)):
        with open(os.path.join(category_dir, document), errors='ignore') as outf:
            tkn_docid += [(token, i) for token in preprocess_document(outf.read())]
        docid_docnm[i] = document
    return (tkn_docid, docid_docnm)

token_docid, doc_ids = get_token_doc_id_pairs('data/mini_newsgroups/rec.autos/')
print(token_docid[:3])   # [('path', 0), ('cantaloupe.srv.cs.cmu.edu', 0), ('das-news.harvard.edu', 0)]

# sort by token
sorted_token_docid = sorted(token_docid, key=itemgetter(0))

def merge_token_in_doc_v2(sorted_token_docid):
    """(token, doc_id) pairs -> (token, doc_id, term_freq) tuples"""
    merged_tokens_in_doc = []
    for token, doc_id in sorted_token_docid:
        if merged_tokens_in_doc:
            prev_tok, prev_doc_id, prev_freq = merged_tokens_in_doc[-1]
            if prev_tok == token and prev_doc_id == doc_id:
                merged_tokens_in_doc[-1] = (token, doc_id, prev_freq + 1)
            else:
                merged_tokens_in_doc.append((token, doc_id, 1))
        else:
            merged_tokens_in_doc.append((token, doc_id, 1))
    return merged_tokens_in_doc

merged_token_in_docs = merge_token_in_doc_v2(sorted_token_docid)
print(merged_token_in_docs[-4:])
# [('zip', 49, 2), ('zx', 79, 1), ('zx-r', 94, 1), ("|'8", 71, 1)]

# split into dictionary and postings
dictionary = defaultdict(lambda: (0, 0))   # term: (doc_freq, total freq)
postings = defaultdict(lambda: [])         # term: [(doc_id, term_freq), ...]

for token, doc_id, term_freq in merged_token_in_docs:
    dictionary[token] = (dictionary[token][0] + 1, dictionary[token][1] + term_freq)

# usually implemented as linked lists
for token, doc_id, term_freq in merged_token_in_docs:
    postings[token].append((doc_id, term_freq))

print(dictionary['zip'], dictionary['zaphod.mps.ohio-state.edu'])   # (1, 2) (51, 52)
print(postings['zip'], postings['zaphod.mps.ohio-state.edu'][:3])   # [(49, 2)] [(3, 1), (14, 1), (17, 1)]

Querying

Boolean queries in the index

With the index built, a query never reads the documents. It fetches the postings list of each query term from the dictionary and combines the lists: AND intersects them, OR unites them, AND NOT subtracts one from the other.

AND query: documents that contain both living and dead

We use a merging algorithm for conjunctive queries, which traverses the postings of the two words simultaneously.

  • Living: 1 → 2 → 5 → 17 → 30 → 31 → 44 → 45 → 47
  • Dead: 5 → 17 → 44
  • Intersection: 5 → 17 → 44
📐 Merging two postings lists

Keep one pointer per list and compare the two document ids: equal → add to the result and advance both; otherwise advance the pointer at the smaller id. It takes linear time in the lengths of the two lists, and it needs the postings of each word to be sorted by document id.

\[ O(x + y), \quad x = df_{\text{living}},\; y = df_{\text{dead}} \]

def and_query(postings, word1, word2):
    """
    merging postings lists of two words
    """
    postings_word1 = postings[word1]
    postings_word2 = postings[word2]

    documents_results = []

    postings_ind1, postings_ind2 = 0, 0
    while postings_ind1 < len(postings_word1) and postings_ind2 < len(postings_word2):
        doc_id1, doc_id2 = postings_word1[postings_ind1][0], postings_word2[postings_ind2][0]
        if doc_id1 == doc_id2:
            documents_results.append(postings_word1[postings_ind1][0])
            postings_ind1 += 1
            postings_ind2 += 1
        elif doc_id1 < doc_id2:
            postings_ind1 += 1
        elif doc_id1 > doc_id2:
            postings_ind2 += 1
    return documents_results

print(postings['living'])   # [(30, 1), (36, 1), (78, 1)]
print(postings['dead'])     # [(29, 1), (36, 1), (65, 1)]
print(and_query(postings, 'living', 'dead'))   # [36]

Questions

1How about if we want to find a document containing \(N\) words?

Intersect the lists two at a time: merge two lists, then merge the result with the next list, and so on. Start with the shortest lists (increasing \(df\)): the intermediate result is never longer than the shortest list seen so far, so every later merge gets cheaper. If some term has \(df = 0\), stop: the answer is empty.

Total time is still linear in the total length of the postings, \(O(\sum_i df_i)\). Try the query planner below.

2What will be the execution time for queries with NOT / OR and different combinations?

x OR y: a union merge, \(O(x + y)\); the result can hold up to \(x + y\) documents.

x AND NOT y: also a merge, \(O(x + y)\); keep the ids of \(x\) that the pointer in \(y\) does not hit.

NOT x on its own: the complement of the list, which means scanning all \(N\) document ids, \(O(N)\).

Combinations such as (a OR b) AND (c OR d): every operator is one linear merge, so the whole query is linear in the total size of the postings involved. To choose an order, estimate each subquery's size (e.g. \(df_a + df_b\) for an OR) and process the smallest first. Switch the operator in the merge widget to compare.

3What are the downsides of Boolean queries?

No ranking: a document either matches or not, so all results look equally good.

Feast or famine: AND of many terms often returns nothing, OR returns far too much.

Exact matching: no synonyms, spelling variants or partial matches; how often a term occurs, or how rare it is, does not matter.

Hard to write: good Boolean queries need expert users; most people type a few words instead. These are the motivations for ranked retrieval.

Optimization

Faster query processing

A merge is linear in the lengths of the postings lists. Two ways to do less work: process the terms in a good order, and skip over parts of long lists.

Process terms in order of increasing frequency

For an AND of many terms, first merge the two terms with the smallest \(df\), then merge the result with the next rarest term, and so on. The intermediate result is never longer than the shortest list, so every later merge is cheaper.

Skip pointers

Can we merge faster than \(O(x + y)\)? Yes, if the index is not changing too fast: add skip pointers to the postings lists at indexing time. They are shortcuts over postings that cannot be in the result.

  • How they are used: when the current id on one list is the smaller one, check its skip pointer. If the skip target is still ≤ the other list's current id, jump there, over everything in between; otherwise advance one posting as usual.
  • Where to place them: a tradeoff. More skips give shorter spans, so skips are taken more often, but cost more comparisons (and space). Fewer skips give fewer comparisons, but long spans that are rarely usable.
  • Heuristic: for a list of length \(L\), use \(\sqrt{L}\) evenly spaced skip pointers. It ignores how query terms are distributed, and it is easy only if the index is fairly static; updates keep changing \(L\).
  • Only for AND: an OR has to visit every posting anyway. Skips exist only on the stored lists, not on intermediate results.
  • ❗ With modern hardware they may not help: loading a bigger postings list can cost more than the faster in-memory merge saves (the lecture cites Bahle et al., 2002).

Phrases

Phrase and proximity queries

We want to answer "stanford university" as a phrase, so that "I went to university at Stanford" is not a match. Users understand phrase queries easily; as many as 10% of web queries are phrase queries. For them, storing only term → documents is no longer enough.

A first attempt: biword indexes

  • Biwords: index every pair of consecutive terms as one dictionary term. "Friends, Romans, Countrymen" gives friends romans and romans countrymen. Two-word phrase queries are then immediate.
  • Longer phrases: stanford university palo alto becomes "stanford university" AND "university palo" AND "palo alto". Without looking at the documents we cannot check that the whole phrase occurs: there can be false positives.
  • Extended biwords: tag the text with parts of speech, group terms into nouns (N) and articles/prepositions (X), and index every sequence of the form N X* N as one term: catcher in the rye is N X X N.
  • Issues: false positives, and a much bigger dictionary. Biword indexes are not the standard solution.

Solution 2: positional indexes

In the postings, store for each document the positions at which the term occurs:

<be: 993427;
  1: 7, 18, 33, 72, 86, 231;
  2: 3, 149;
  4: 17, 191, 291, 430, 434;
  5: 363, 367, …>
  • Phrase queries: fetch the entries of each distinct term (for "to be or not to be": to, be, or, not), start from the rarest, and merge their doc:position lists. Now a document must not only contain both terms: be must occur at a position one higher than to, and so on.
  • Proximity queries: LIMIT! /3 STATUTE /3 FEDERAL /2 TORT, where /k means "within \(k\) words of" (on either side). The same merge works with a positional index; a biword index cannot answer these.

Positional index size

A positional index needs an entry for every occurrence, not one per document, so its size depends on document length. An average web page has fewer than 1,000 terms; SEC filings, books and even some epic poems easily reach 100,000. For a term with frequency 0.1%:

Document sizePostingsPositional postings
1,00011
100,0001100
  • Rules of thumb (English-like languages): a positional index is 2–4 times as large as a non-positional one; compressed, it takes about 35–50% of the volume of the original text.
  • It is still the standard, because phrase and proximity queries are so useful, whether users type them or a ranking system uses them implicitly.

Combination schemes

  • For frequent phrases such as "Michael Jackson" or "Britney Spears", merging positional lists again and again is wasteful; even more so for "The Who", whose words are very common while the phrase is rare. Keep such phrases in a biword (phrase) index and use the positional index for the rest.
  • Williams et al. (2004) also add a next-word index: a typical mixture of web phrase queries ran in ¼ of the time of a positional index alone, using 26% more space.
  • Zones (from the notebook): restrict a term to one part of the document, e.g. the Subject or From header of a post, the title or the author.

Doc 1 (7, 18, 33, 72, 86, 231): no pair 4 apart. Doc 2 (3, 149): no. Doc 4: 430 and 434. Doc 5: 363 and 367. So only docs 4 and 5 can contain it.

5Adapt the linear merge of postings to handle proximity queries. Can you make it work for any value of \(k\)?

Merge the two postings lists by document id as before. For a document in both lists, walk its two position lists with two pointers, like a second merge: for each position \(p_1\) of the first term, keep a window of the positions \(p_2\) of the second term with \(|p_1 - p_2| \le k\), dropping positions that fall behind and adding those that come into range. Every pair in the window is a match.

Each position enters and leaves the window once, so the work is linear in the number of positions plus the number of matches, for any \(k\) (IIR, Figure 2.12).

Summary: key takeaways

  1. Boolean retrieval: the answer is the set of documents that satisfy the query; an index built once, in advance, replaces scanning the text for every query.
  2. Pipeline: documents → tokenizer → linguistic modules → indexer → inverted index.
  3. Incidence matrix: terms × documents; queries become bitwise operations on rows, but the matrix is almost all zeros.
  4. Inverted index: a dictionary of terms with their \(df\), each pointing to a postings list of document ids sorted by id.
  5. Tokens to terms: tokenization, normalization, case folding, stop words, stemming or lemmatization; each choice trades recall against precision. Our preprocess_document: tokenize, drop punctuation, lower-case.
  6. Construction: collect (token, doc_id) pairs → sort by token → merge into (token, doc_id, tf) → split into dictionary and postings.
  7. Queries: AND, OR, AND NOT are linear merges of sorted postings lists, \(O(x + y)\); a lone NOT costs \(O(N)\).
  8. Faster merges: process terms by increasing \(df\); skip pointers (\(\sqrt{L}\) per list, AND only) jump over parts of long lists.
  9. Phrases: biword indexes are fast for two words but give false positives; positional indexes answer phrase and proximity queries, at 2–4 times the size.
