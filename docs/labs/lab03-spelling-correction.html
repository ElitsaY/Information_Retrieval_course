Tolerant Retrieval and Spelling Correction

Overview of the lab

Goal: find documents even when the query does not match the dictionary exactly: the user misspells a word or spells a name as it sounds. The lab goes with the lecture on tolerant retrieval (IIR, chapter 3).

  1. Spelling correction: its uses and flavors, and what we need before we start (a list of correct words).
  2. Edit distance: how far apart two words are, computed by dynamic programming.
  3. Finding candidates fast: n-gram overlap, the Jaccard coefficient, tries.
  4. Context and choosing a suggestion: flew form Heathrow, "Did you mean", thesauri.
  5. Soundex: matching names by how they sound.
  6. Putting it together: which queries the engine can now answer.

Spelling correction: uses and flavors

  • Two uses: correcting the documents being indexed, and correcting the query, our main focus. For a query we can either retrieve documents indexed by the correct spelling, or suggest alternative queries: Did you mean …?
  • Isolated-word correction: check each word on its own. It cannot catch typos that are real words: from → form.
  • Context-sensitive correction: look at the surrounding words: I flew form Heathrow to Narita.
  • Domain knowledge helps: OCR confuses O and D more often than O and I, which are the likely pair when typing (adjacent on the QWERTY keyboard).

Prerequisite: a list of words at hand

Isolated-word correction rests on one premise: there is a lexicon the correct spellings come from. Given the lexicon and a character sequence \(q\), return the lexicon words closest to \(q\).

  • A public list of all words in a language: e.g. Google Books Ngrams, Project Gutenberg, a standard dictionary, or a hand-maintained industry-specific lexicon.
  • The words in the indexed documents: this covers names, acronyms and domain terms, but it also contains the misspellings. You can add domain-specific words by hand.

💡 In this lab the lexicon is the dictionary of the 100 sci.crypt posts from Lab 01: 4,389 words made of letters only, each with its document frequency. It shows the downside of a corpus lexicon: goverment (2 posts), govenment and geovernment are in it, next to government (31 posts).

Finding the correct word: edit distance

To pick the lexicon words "closest" to a misspelled query we need a distance between strings. The standard one counts single-character edits.

📐 Edit (Levenshtein) distance

The minimum number of single-character edits that turn \(s_1\) into \(s_2\). The edits are insert, delete and replace a character. E.g. the edit distance from cat to dog is 3. It is solved with dynamic programming in \(O(|s_1| \cdot |s_2|)\) time.

Edit distance algorithm

Cell \(m[i, j]\) holds the edit distance between the first \(i\) letters of \(s_1\) and the first \(j\) letters of \(s_2\).

  1. Initialize the matrix with zeros; it has \(|s_1|+1\) rows and \(|s_2|+1\) columns.
  2. Initialize the first row and column with the numbers from 0 to \(|s_2|\) and from 0 to \(|s_1|\): the cost of building a prefix by inserting letters, starting from the empty string.
  3. Every other cell is the cheapest of three moves:
\[ m[i,j] = \min\begin{cases} m[i-1,j] + 1 & \text{delete } s_1[i] \\ m[i,j-1] + 1 & \text{insert } s_2[j] \\ m[i-1,j-1] + \begin{cases}0 & s_1[i] = s_2[j]\\ 1 & \text{otherwise}\end{cases} & \text{replace (or keep)} \end{cases} \]
  1. The minimum edit distance is in the last cell, \(m[|s_1|, |s_2|]\).

edit_distance.py (a solution) Python ▾ 
import numpy as np

def edit_distance(s1, s2):
    """
    Return the minimum edit distance between the two words
    """
    m = np.zeros((len(s1) + 1, len(s2) + 1), dtype=int)
    m[:, 0] = range(len(s1) + 1)     # delete every letter of s1
    m[0, :] = range(len(s2) + 1)     # insert every letter of s2
    for i in range(1, len(s1) + 1):
        for j in range(1, len(s2) + 1):
            m[i, j] = min(m[i - 1, j] + 1,                            # delete s1[i-1]
                          m[i, j - 1] + 1,                            # insert s2[j-1]
                          m[i - 1, j - 1] + (s1[i - 1] != s2[j - 1]))  # replace or keep
    return m[-1, -1], m

print(edit_distance('sunday', 'saturday')[0])     # 3
print(edit_distance('elephant', 'relevant')[0])   # 3
print(edit_distance('lullaby', 'lollipop')[0])    # 5

Variants

  • Weighted edit distance: the cost of an operation depends on the characters involved, to capture keyboard errors (m is more likely mistyped as n than as q) or OCR errors (different weights). It needs a weight matrix as input; some literature treats the weight as the probability of the error.
  • Damerau–Levenshtein: also allow swapping two adjacent letters as one edit. smtih → smith costs 1 instead of 2 (try it with transpositions on).

Some implementations

  • pyxDamerauLevenshtein: Damerau–Levenshtein distance in Cython, for speed.
  • Peter Norvig's spelling corrector: generate every string at edit distance 1 and 2 from the word, keep those that are real words, and pick the most probable one (a language model, with priority to fewer edits). It can include an error model, e.g. from lists of common errors (aspell test data).
  • TextBlob: contains a spellchecker trained on text (from Project Gutenberg), based on Norvig's idea. In the notebook: TextBlob("I havv goood speling!").correct() gives I have good spelling!
  • Corpora of real misspellings, for testing: Roger Mitton's collection.

Finding candidates fast: n-gram overlap and tries

A problem with the edit distance approach: do we compute the edit distance from the query to every dictionary term? That is slow. We first cut the dictionary down to a few plausible candidates, and compute edit distances only for those.

Solution 1: a character n-gram index

📐 n-gram

A sequence of \(n\) consecutive items. Here the items are characters, so a character n-gram is \(n\) letters in a row inside a word. With \(n = 2\) we call them bigrams, with \(n = 3\) trigrams. A word of \(L\) letters has \(L - n + 1\) n-grams.

Example, the word castle (6 letters):

  • bigrams (\(6 - 2 + 1 = 5\)): ca as st tl le
  • trigrams (\(6 - 3 + 1 = 4\)): cas ast stl tle

The items can also be words: the biwords of Lab 01 are word bigrams (friends romans, romans countrymen).

  • Build a character n-gram index: n-gram → the words containing it (av → avocado, pavement, …).
  • Retrieve the postings of every n-gram of the query and merge them, counting how many n-grams each word shares with the query.

    Example: the misspelled query bord has the bigrams bo or rd. In a small dictionary of eight words, their postings are:

    • bo → aboard, about, boardroom, border
    • or → border, lord, morbid, sordid
    • rd → aboard, ardent, boardroom, border, lord, sordid

    Merging the three lists gives the number of shared bigrams:

    • 3: border
    • 2: aboard, boardroom, lord, sordid
    • 1: about, morbid, ardent

    Words that share no bigram with bord are never looked at.

  • Normalize: a raw count favours long words (car shares all its bigrams with carbon). Use the Jaccard coefficient of the two n-gram sets and declare a match above a threshold.
  • Then rank the candidates by edit distance (and, among equals, by how common the word is).
📐 Jaccard coefficient

For two sets \(X\) and \(Y\) (here: the n-grams of two words). It is 1 when the sets are equal and 0 when they are disjoint; the sets need not have the same size.

\[ J(X, Y) = \frac{|X \cap Y|}{|X \cup Y|} \]

The union does not have to be built: \(|X \cup Y| = |X| + |Y| - |X \cap Y|\). The intersection size is exactly the count from the merge above.

Our example: the query bord has \(|X| = 3\) bigrams (bo or rd). For each word from the postings lists (shared bigrams highlighted):

The raw count tied aboard, boardroom, lord and sordid at 2. Jaccard tells them apart: the short lord moves up to 0.50, the long boardroom drops to 0.22, because its 6 extra bigrams enlarge the union. With a threshold of 0.5, only border and lord stay as candidates.

💡 The postings scan only needs each term's number of n-grams, not the term itself: when scanning for bord reaches boardroom with 2 matching bigrams, and boardroom has 8 bigrams, \(J = 2 / (8 + 3 - 2)\) (IIR 3.3.4). The lecture's example slide is titled "trigrams" but uses the bigrams of lord (lo, or, rd).

Exercise 3: implement the n-gram overlap spell-checker and find the best Jaccard threshold for your dataset. A solution with the notebook's function names:

ngram_spellcheck.py (a solution) Python ▾ 
from collections import defaultdict, Counter

def get_word_ngrams(word, n):
    return [word[i:i+n] for i in range(len(word)-n+1)]

def build_ngram_postings(n, tokenized_documents):
    """
    Create postings from the tokenized documents -
    For each n-gram we want to have the list of words, containing that n-gram. (E.g. av: [avocado, pavement, ...])
    """
    vocabulary = sorted({token for doc in tokenized_documents for token in doc})
    postings = defaultdict(list)
    for word in vocabulary:                        # each word once per n-gram
        for gram in set(get_word_ngrams(word, n)):
            postings[gram].append(word)
    return postings

def ngram_spellcheck(word, postings, n, jaccard_threshold=0.7):
    """Return the words from the postings structure, which are closest to the input word."""
    query = set(get_word_ngrams(word, n))
    shared = Counter()                             # merge the postings: word -> number of shared n-grams
    for gram in query:
        shared.update(postings.get(gram, []))
    scored = []
    for candidate, common in shared.items():
        size = len(set(get_word_ngrams(candidate, n)))
        jaccard = common / (len(query) + size - common)
        if jaccard >= jaccard_threshold:
            scored.append((candidate, jaccard))
    return sorted(scored, key=lambda x: -x[1])

Discussion: how n changes the Jaccard coefficient

The same pair of words gets a different Jaccard coefficient for every \(n\). Take the misspelled query algorythm and three dictionary words: the intended algorithm (one letter replaced), its anagram logarithm, and rhythm.

algorythm vs\(n = 1\) (letters)\(n = 2\) (bigrams)\(n = 3\) (trigrams)
algorithm (intended)8/10 = 0.806/10 = 0.604/10 = 0.40
logarithm8/10 = 0.802/14 = 0.141/13 = 0.08
rhythm5/9 = 0.563/10 = 0.302/9 = 0.22
  • Small \(n\) is lenient but ignores order: with single letters, algorithm and logarithm are the same set, so they tie at 0.80. For the same reason teh → the scores 1.0, and so does any other anagram.
  • Larger \(n\) keeps the order: the wrong words drop fast (logarithm from 0.80 to 0.14 to 0.08), so fewer false candidates pass the threshold.
  • But larger \(n\) also punishes the typo more: one wrong letter sits inside up to \(n\) different n-grams, and breaks all of them. The intended word drops from 0.80 to 0.60 to 0.40.
  • Small \(n\) lets the right word in, and many wrong ones with it.
  • Big \(n\) keeps the wrong words out, and often the right one too.
  • When you raise \(n\), lower the threshold.

A small example

Someone types silemt (m is next to n on the keyboard) and means silent. The dictionary also has three anagrams of silent: listen, tinsel, enlist. The threshold is 0.6.

  • Big \(n\) keeps them out, and the right word too: with bigrams or trigrams the anagrams drop to 0, but silent drops to 0.43 and 0.33, below 0.6.
  • So lower the threshold: 0.4 for bigrams or 0.3 for trigrams, and only silent passes.

Jaccard vs overlap coefficient

📐 Overlap coefficient

It also compares two sets \(X\) and \(Y\). It divides the size of the intersection by the size of the smaller set:

\[ O(X, Y) = \frac{|X \cap Y|}{\min(|X|, |Y|)} \]

It is 1 when the smaller set sits completely inside the larger one, however large the larger one is. Jaccard divides by the union, so every extra element in either set lowers it.

With our query bord (3 bigrams):

  • border: overlap \(3/3 = 1.00\), Jaccard \(3/5 = 0.60\)
  • lord: overlap \(2/3 = 0.67\), Jaccard \(2/4 = 0.50\)
  • boardroom: overlap \(2/3 = 0.67\), Jaccard \(2/9 = 0.22\)

The overlap coefficient gives lord and boardroom the same score, because it ignores the 6 extra bigrams of boardroom. For spelling correction this favours long words: car has all its bigrams in carbon, so their overlap coefficient is 1, while Jaccard gives \(2/5 = 0.40\).

5Answer to Exercise 5.

Jaccard: \(50 / 100 = 0.5\), and it does not change: moving 10 words from \(A\) to \(B\) keeps the intersection (50) and the union (100).

Overlap coefficient: \(|A| + |B| = 100 + 50 = 150\). With \(|A| = |B| = 75\) it is \(50 / 75 \approx 0.67\); with \(|A| = 65, |B| = 85\) it is \(50 / 65 \approx 0.77\). It grows as the smaller set shrinks and reaches 1 when one set is contained in the other, however large the other is. Jaccard only looks at intersection and union, so it does not care how the rest is split.

Recap: the problem

To correct a word, we need the dictionary words closest to it. The direct way computes the edit distance from the query to every word in the dictionary. One edit distance fills a table of \(|s_1| \cdot |s_2|\) cells. With a 10-letter query and a dictionary of 100,000 words of about 8 letters, that is about 8 million cells for one query word. This is far too slow for a search engine.

Solution 1 skips most of these comparisons: the n-gram index keeps only the words that share enough n-grams with the query, and we compute the edit distance only for them. Solution 2 still uses edit distance, but it computes the common start of similar words only once, and it stops early on words that are already too far.

Solution 2: tries

To correct lates we might compute the edit distance to late, latest and latte, and every time we recompute the rows for the common prefix lat. Store the whole vocabulary in a trie, where each node is one letter and its branches are the letters that can follow; then each prefix's row of the edit-distance table is computed once, and branches whose row is already above the limit are cut off (Steve Hanov's post).

Lecture

Context and choosing a suggestion

Isolated-word correction cannot fix flew form Heathrow: every word is spelled correctly. If the phrase query matches no documents, we would like to answer Did you mean "flew from Heathrow"?

  • First idea: for each query word, retrieve the dictionary terms close to it in (weighted) edit distance, then try the phrases with one word replaced at a time (flew from heathrow, fled form heathrow, flea form heathrow, …) and suggest the one with many hits. With 7 alternatives for flew, 19 for form and 3 for heathrow that is 7 + 19 + 3 = 29 phrases; trying every combination would be far more (8 · 20 · 4 = 640, counting each original word as an option).
  • Another approach: break the phrase into a conjunction of biwords (Lab 01), look for biwords that need only one term corrected, and keep only frequent ones (flew from rather than fled fore) before extending them to the next word.
  • Which suggestion to show? Many alternatives are enumerated for "Did you mean"; show one or a few. Heuristics: the alternative that hits the most documents, and query-log analysis for especially popular, topical queries.
  • Cost: spelling correction is computationally expensive. Run it only on queries that matched few documents, not routinely on every query.
  • Caveat: everything depends on what the index token is. In Chinese and Japanese, spelling correction is poorly defined.

Thesauri and query expansion

  • Thesaurus: a language-specific list of synonyms for terms likely to be queried (car → automobile); a hand-made alternative to edit distance. Machine learning can help build it.
  • Query expansion, not index expansion: rewrite the query rather than the index. No index blow-up, but query processing slows down. It may retrieve more junk: puma → jaguar retrieves documents about cars instead of sneakers.
Lecture

Soundex

Some misspellings come from typing a word as it sounds, mostly names: chebyshev vs tchebycheff. Soundex heuristics give every term a phonetic hash so that similar-sounding terms get the same code. Language specific, mainly for names.

  • Index: turn every token into a 4-character code and build an index from codes to terms; do the same with query terms, and search this index when the query asks for a Soundex match.
  • Why it works: vowels are treated as interchangeable when transcribing names, and consonants with similar sounds (like D and T) share a digit.
📐 Soundex, the typical algorithm
  1. Keep the first letter of the word.
  2. Change A, E, I, O, U, H, W, Y to 0.
  3. Change letters to digits: B F P V → 1; C G J K Q S X Z → 2; D T → 3; L → 4; M N → 5; R → 6.
  4. Repeatedly remove one out of each pair of consecutive identical digits.
  5. Remove all zeros.
  6. Pad with trailing zeros and return the first four positions: a letter and three digits. Herman becomes H655.

💡 Step 4 on the slide reads "remove all pairs of consecutive digits". It should be one of each pair of identical consecutive digits (IIR): Hermann → H 0 6 5 0 5 5 → H 0 6 5 0 5 → H655, the same code as Herman.

Big picture

Putting it together

We now have a basic inverted index with skip pointers, spelling correction and Soundex. Together they can answer queries such as

(SPELL(moriset) /3 toronto) OR SOUNDEX(chaikofski)
  • Language detection: many of these components need to know the language. For documents and paragraphs there is enough text for machine learning; for queries it is much harder, so add other cues (client settings, the domain the query comes from).
  • Results caching: if 25% of your users search for britney AND spears, you probably need spelling correction, but you do not need to keep intersecting those two postings lists. The web query distribution is extremely skewed, so caching results for common queries pays off.
  • Design choices: does stemming happen before the Soundex index? What about n-grams? How is a query parsed and dispatched to the different indexes?

Summary: key takeaways

  1. Tolerant retrieval: map a query term to the dictionary terms the user meant, then run the normal query; correction needs a lexicon of correct words.
  2. Edit distance: insert, delete, replace; a dynamic-programming table in \(O(|s_1| \cdot |s_2|)\); weighted and transposition variants.
  3. Candidates: never compare the query with every term. Use an n-gram index and the Jaccard coefficient to shortlist, then rank by edit distance; a trie shares the work for common prefixes.
  4. Context: fix one word at a time or use biwords, choose the suggestion with the most hits, and run correction only when a query finds little.
  5. Soundex: a 4-character phonetic code (letter + 3 digits) for matching names that sound alike.
