What are web crawlers?

Definition

Web crawler

A web crawler (crawler, web spider) is a program that searches and automatically indexes website content and other information over the internet. Alternatively: crawlers are software or scripts programmed to systematically browse the World Wide Web as part of an automated process.

  1. Step 1: the crawler starts processing a predefined list of web pages.
  2. Step 2: once it crawls a page, it discovers new pages via hyperlinks.
  3. Step 3: it adds the newly discovered URLs to the crawl queue, to be crawled later.

Result: a crawler can explore every page that is connected to the ones it already knows. It does not magically know every URL on the Web.

What are they used for?

  • Search engines: Googlebot, Bingbot, Applebot (Siri and Spotlight), OpenAI's crawlers for ChatGPT, and Xenon, a crawler the Dutch tax administration has used since 2004 to find undeclared online sellers.
  • Web scraping: data analytics and data science, marketing and sales, competition research, and academic research (especially with the machine-learning advances of recent years).
  • Data analytics.

See it: types of web crawlers

The taxonomy of Kumar, Bhatia & Rattan (2017), A survey of Web crawlers for information retrieval. Click a type.

Crawling vs scraping

1A client extracts large amounts of sports data with a framework that executes "crawlers". Looking at the architecture, you see that a separate "crawler" is implemented for every web page of interest. How does this align with the definition of a crawler?

It does not: these are scrapers. Web scraping extracts specific data from one or more websites, with code written for each page's layout. Crawling extracts the whole page and the additional URLs it links to, and one crawler works on any page.

2Does a web crawler exclude the use of a web scraper? How do crawlers and scrapers scale?

No, they combine: a crawler detects pages, then scrapers extract specific information rather than the whole page content. This is used when the target domain is clear. Crawlers are always used at large scale; scrapers at small and large scale.

Part II

How a crawler works

Start from one page, https://example.org/. Fetch it and find links to /about, /courses, /people. Fetch those and discover more links. The process is recursive.

crawl_loop.py (conceptual) Python ▾ 
frontier = [seed_url]
visited = set()

while frontier:
    url = frontier.pop()

    if url in visited:
        continue

    page = fetch(url)
    visited.add(url)

    store(page)

    for link in extract_links(page):
        frontier.append(link)

This is enough to explain the idea. It is not enough to build a responsible production crawler.

Crawler architecture

A slightly more realistic pipeline. It is a loop: the links a page yields go back into the frontier. Click a stage.

  • Seed URLs: a crawler must start somewhere: a university homepage, a news homepage, a known domain list, a sitemap, a previous crawl. The seed set strongly affects what the crawler discovers.
  • URL frontier: the collection of URLs waiting to be crawled. A naive implementation uses a list, a queue or a stack; a real crawler needs scheduling: Which URL should be fetched next? Which host was contacted recently? Which pages are likely to be important? Which should be revisited? How do we avoid crawling one site too aggressively?
Part III

URLs are messier than they look

Are https://example.org/page, https://example.org/page/, https://example.org/page#section and https://EXAMPLE.org/page four different documents? Maybe. Maybe not. This introduces URL normalization and canonicalization.

  • Normalization steps: lowercase the hostname, remove URL fragments, resolve relative URLs, remove default ports, normalize path components (https://example.org/a/../page → https://example.org/page).
  • ❗ Normalization must be conservative. Different URLs can genuinely represent different resources: /page and /page/ may differ, and so may ?id=1 and ?id=2.

💡 Try URL normalization yourself: visit lab06/url_normalization.py in the course GitHub repository. It normalizes a list of links found on one page, prints each link next to its normalized form, and counts how many different pages are left. Set AGGRESSIVE = True to also apply the steps that are not safe (drop the trailing slash, drop tracking parameters, sort query parameters), and compare the counts.

Why duplicate URLs matter

Without duplicate handling, with links A → B, A → C, B → C, C → A, the crawler keeps rediscovering A, B, C, A, B, C, … At minimum, maintain visited_urls = set(). But there is a second problem: different URLs → the same or nearly identical content: printer-friendly pages, tracking-parameter variants, mobile/desktop versions, mirrored pages, session-specific URLs. So we distinguish a URL duplicate from a content duplicate.

Definition

Exact duplicate detection

Hash the (normalized) content: if the same content produces the same hash, it is an exact duplicate.

fingerprint.py Python ▾ 
import hashlib

fingerprint = hashlib.sha256(
    text.encode("utf-8")
).hexdigest()
Part IV

robots.txt and politeness

robots.txt

A website can publish a file at /robots.txt, e.g. https://example.org/robots.txt. The file says which parts of the site crawlers may visit and which they should skip.

Definition

Example: https://example.org/robots.txt

User-agent: *
Allow: /private/press/
Disallow: /private/
Disallow: /search

User-agent: * means the rules apply to all crawlers, so also to ours. Each rule is a path prefix: it covers every URL that starts with it.

What our crawler, MyCourseCrawler, may fetch on example.org:

URL pathMyCourseCrawlerWhy
/✅ allowedno rule matches
/courses/ir✅ allowedno rule matches
/private/admin❌ not allowedDisallow: /private/
/private/press/news✅ allowedAllow: /private/press/ is more specific than Disallow: /private/
/search?q=crawler❌ not allowedDisallow: /search

Can a crawler break the rules?

Yes. robots.txt only states what the site owner wants, and nothing on the server enforces it. A crawler that ignores it can still fetch /private/, but sites notice this and block such crawlers. ❗ So robots.txt does not protect anything: sensitive pages need real access control.

Politeness

Even when robots.txt allows a page, a crawler should not overwhelm the server. Wait between requests to the same host, don't send many requests to one host at once, and slow down when the server answers 429 Too Many Requests. Too many requests can overload the server, and then the site blocks the crawler.

Crawl traps

Some sites generate effectively unlimited URL spaces. A crawler needs heuristics and limits, otherwise the frontier explodes.

  • Calendars: ?year=2026, ?year=2027, ?year=2028, …
  • Session identifiers: ?id=123, ?id=456, … the same page under endless names.
  • Honeypot traps: links in the HTML that only bots see, not human visitors. A crawler that follows them identifies itself as a bot that ignores the page as a user sees it.
Part V

What is BeautifulSoup?

BeautifulSoup is a Python library that reads an HTML page and turns it into a tree of elements: the tags (<h2>, <div>, <a>, …), their attributes (class, id, href) and the text inside them. You then search the tree for the parts you need. It does not download anything: requests fetches the HTML and BeautifulSoup parses it.

💡 The most common calls (find, find_all, get_text, attributes, select_one, select, find_next_sibling) are in lab06/bs_basics.py in the course repository. It parses a small job-list page and prints each call next to what it returns. Run python bs_basics.py, then change the HTML or the calls and run it again.

Example: title, location and description of a job ad

We want the job title, the location and the description from this Google Careers job ad. The link we were given ended with ?_gl=1*1bdp7z1*…. These are tracking parameters, so we remove them first (Part III). Google's robots.txt allows job pages for all crawlers; it only blocks the search result pages (.../jobs/results?page=).

Two things make this page harder than the small example. Next to the job, the page lists about 20 other jobs, so the first <h2> and the first location on the page may belong to something else. We first find the block with the job details and then search only inside it. Also, class names such as DkhPwc and r0wTof are generated by Google's tools and can change at any time. A visible text such as "About the job" usually stays the same longer.

job_page.py Python ▾ 
import requests
from bs4 import BeautifulSoup

URL = ("https://www.google.com/about/careers/applications/jobs/results/"
       "78511373281043142-staff-machine-learning-engineer-youtube-live-discovery")
HEADERS = {"User-Agent": "IRCourseBot/0.1 (student lab crawler)"}

soup = BeautifulSoup(requests.get(URL, headers=HEADERS, timeout=10).text, "html.parser")

# the page also lists other jobs, so the obvious searches find the wrong thing
soup.find("h2").get_text(strip=True)
# 'Jobs search results'
len(soup.select("span.r0wTof"))               # a location for every job in the list
# 29

# so first find the block with the job details, then search only inside it
job = soup.select_one("div.DkhPwc")

title = job.find("h2").get_text(strip=True)
# 'Staff Machine Learning Engineer, YouTube Live Discovery'
location = job.select_one("span.r0wTof").get_text(strip=True)
# 'Mountain View, CA, USA'

# the description: the paragraphs after the heading "About the job"
about = job.find("h3", string="About the job")
description = "\n".join(p.get_text(" ", strip=True) for p in about.find_next_siblings(["p", "div"]))
len(description.split())
# 346
description[:60]
# "Google's software engineers develop the next-generation tech"

Part VI

Scraping static and dynamic content

Static content

The examples of static and dynamic content use three Bulgarian news sites: btvnovinite.bg, nova.bg and petel.bg. The robots.txt of all three allows crawling these pages. Before you scrape any site, check its robots.txt and terms of use, and keep your request rate low.

On a static page the content is already in the HTML the server sends. The news list of btvnovinite.bg/bulgaria/?page=4 is like this: open the page source (Ctrl + U) and you will find the headlines there. Every page of the list has its own URL (?page=4, ?page=5, …), so a scraper only has to change the number. The notebook leaves getPropertyFromPage as an exercise; one possible solution:

static_page.py Python ▾ 
import time
import requests
from urllib.parse import urljoin
from bs4 import BeautifulSoup

HEADERS = {"User-Agent": "IRCourseBot/0.1 (student lab crawler)"}

def getPropertyFromPage(url):
    """
    Visit the page and choose some properties to crawl from the parser
    """
    html = requests.get(url, headers=HEADERS, timeout=10).text
    document = BeautifulSoup(html, "html.parser")
    news = document.select(".left-part-listing-news a.small-title")   # the main news list only
    return {
        "title": document.title.get_text(strip=True),
        "headlines": [a.get_text(strip=True) for a in news],
        "links": [urljoin(url, a["href"]) for a in news],             # relative → absolute
    }

page = getPropertyFromPage("https://btvnovinite.bg/bulgaria/?page=4")
page["title"]
# 'България - bTV Новините - страница 4'
len(page["headlines"])
# 13   (the headlines themselves change as new news comes in)
page["links"][0]
# 'https://btvnovinite.bg/bulgaria/...'

for n in [5, 6]:                                  # the next pages: only the number changes
    time.sleep(1)                                 # be polite: wait between requests
    p = getPropertyFromPage(f"https://btvnovinite.bg/bulgaria/?page={n}")
    print(n, len(p["headlines"]))
# 5 13
# 6 13

Dynamic content

Many pages load their content with JavaScript: when you scroll (infinite scroll) or click a button such as "Load more". This content is not in the HTML that requests downloads. On some pages the first HTML has no content at all.

Solution✅ Pros❌ Cons
1. Naive, semi-automatic: open the page, scroll down as far as necessary, save it (Ctrl + S)easy; surprisingly helps with hard-to-crawl websitesa lot of manual work; not scalable
2. Fully automatic: a browser-automation tool (Selenium, Playwright) scrolls and renders the pageovercomes dynamic content; complex logic; scalesrequires deeper understanding; much slower in most cases
Extra option: find the JavaScript's data source (the browser's Network tab) and request it directlyfast, no renderingworks only when such an endpoint exists; it can change without notice

Not all dynamic pages are the same: some load content through requests you can see in the Network tab, others embed it as JSON in the page. nova.bg/news uses the first kind. Its first 24 headlines are in the HTML, and below them is a "Виж още" (See more) button. Each click sends POST /news/getmorenews/2, then /3, and so on, and the server answers with an HTML fragment of 24 more headlines. We can send the same request ourselves (the extra option):

more_news.py Python ▾ 
import time
import requests
from bs4 import BeautifulSoup

HEADERS = {"User-Agent": "IRCourseBot/0.1 (student lab crawler)"}

def more_news(n):
    """Return the headlines that the n-th "Виж още" click loads."""
    r = requests.post(f"https://nova.bg/news/getmorenews/{n}", headers=HEADERS, timeout=10)
    fragment = BeautifulSoup(r.text, "html.parser")   # an HTML fragment, not a full page
    return [a.get_text(strip=True) for a in fragment.select(".thumb-title a")]

for n in [2, 3]:
    print(n, len(more_news(n)))
    time.sleep(1)                                     # be polite: wait between requests
# 2 24
# 3 24

A second example, with infinite scroll: petel.bg/novini/Novini-__1__2. The page arrives with 200 news items in the HTML. When you scroll to the bottom, its script asks for the next page with $.getJSON(".../Novini-__1__3"), adds the items to the list and changes the address bar to ...__1__3. It is the same URL as the next page, but the answer is different. The script sends the header X-Requested-With: XMLHttpRequest, and with it the server returns JSON instead of a full HTML page. In the JSON, data holds the HTML of the 200 items, and next is the number of the page after it.

infinite_scroll.py Python ▾ 
import time
import requests
from bs4 import BeautifulSoup

URL = "https://petel.bg/novini/Novini-__1__{}"
HEADERS = {
    "User-Agent": "IRCourseBot/0.1 (student lab crawler)",
    "X-Requested-With": "XMLHttpRequest",   # what the page's own script sends: the server answers with JSON
}

def load_page(n):
    data = requests.get(URL.format(n), headers=HEADERS, timeout=10).json()
    items = BeautifulSoup(data["data"], "html.parser").select("article h3")   # "data" holds HTML
    return data, [h.get_text(strip=True) for h in items]

data, headlines = load_page(3)
data["currentPage"], data["prev"], data["next"], data["perPage"]
# (3, 2, 4, 200)
len(headlines)
# 200

n = data["next"]
for _ in range(2):                            # "scroll" two more times
    time.sleep(1)                             # be polite: wait between requests
    data, headlines = load_page(n)
    print(data["currentPage"], len(headlines))
    n = data["next"]
# 4 200
# 5 200

# without the header, the same URL gives the normal HTML page
requests.get(URL.format(3), headers={"User-Agent": HEADERS["User-Agent"]}, timeout=10).headers["Content-Type"]
# 'text/html; charset=UTF-8'

How to crawl without getting blocked

  • Use a proxy: rotate IP addresses (proxy rotation).
  • Reduce the number of crawls for specific web pages.
  • Change the crawling pattern: introduce random clicks, scrolls and mouse movements, and randomize the exact execution time without a range.
  • Be careful with honeypot traps: links in the HTML code that are only visible to bots, not to organic users. They are very rare nowadays, because the effort required does not outweigh the result, and there are workarounds for such traps.
  • Commercial solution: get your IPs whitelisted by different web pages (usually there is a contract with the permitted number of crawls per day, week or month).
  • Research lab solution: buy 1 million IPs to use as proxies when crawling fake news data.

Good practices when building large-scale web crawlers

  • Ensure you have full access to the server.
  • Identify slow websites, e.g. with the TTFB (time to first byte) metric.
  • Crawl during low-traffic (off-peak) hours.
  • Use a fast and stable internet connection, preferably Ethernet, as Wi-Fi is slower and less reliable.
  • If possible, run crawlers on a server (cloud compute) instead of a desktop. This applies to big-scale crawling.
  • Partial crawls: crawl a single website with multiple continuous crawlers, each focusing on a different section. That way things stay simple and everything is updated faster with up-to-date data.
  • Ignore URL parameters and other URLs that are duplicates of a canonical URL.
