Learning objectives

Relevance judgments

For each query–document pair, a human assessor assigns a label: relevant or not relevant, or a grade such as 0 = not relevant, 1 = somewhat relevant, 2 = relevant, 3 = highly relevant. Once we have ranking + relevance, we can calculate metrics.

Part II

Precision and Recall

A toy ranking used throughout: D1 (relevant), D2 (not), D3 (relevant), D4 (not), D5 (relevant), written R N R N R. The collection contains exactly these three relevant documents: D1, D3, D5.

📐 Precision and Recall
\[ \text{Precision} = \frac{\text{relevant retrieved}}{\text{retrieved}} \qquad \text{Recall} = \frac{\text{relevant retrieved}}{\text{all relevant}} \]

Precision: of the documents we retrieved, how many are relevant? Recall: of all relevant documents that exist, how many did we retrieve? For ranked retrieval we compute them at a cutoff \(k\): P@1, P@5, P@10, …

  • Toy ranking: \(P@1 = 1/1 = 1.0\), \(P@3 = 2/3\), \(P@5 = 3/5 = 0.6\). \(Recall@3 = 2/3\) (2 of the 3 relevant documents found), \(Recall@5 = 1.0\).
  • They answer different questions. With 10 relevant documents: system A retrieves 2, both relevant: Precision 1.0, Recall 0.2. System B retrieves 100, 10 of them relevant: Precision 0.1, Recall 1.0. Neither measure is universally more important.
  • Retrieval depth: as we retrieve more and more documents, recall tends to increase and precision often decreases. This is a tendency, not a guarantee for every single step: a relevant document at rank \(k\) raises P@k.

Part III

Why rank position matters

Ranking A is R R R N N N N N N N, ranking B is N N N N N N N R R R. Both have \(P@10 = 0.3\), yet ranking A is clearly preferable for most users (load both in the playground above). We need rank-aware metrics.

Reciprocal Rank and MRR

📐 Reciprocal Rank
\[ RR = \frac{1}{r} \qquad MRR = \frac{1}{|Q|} \sum_{q \in Q} RR(q) \]

\(r\) is the rank of the first relevant result: at rank 1, RR = 1; at rank 2, 0.5; at rank 5, 0.2. With no relevant result, RR = 0. RR is for one query, MRR is the mean across queries.

  • Useful when the user mainly wants one good result: navigational search, entity lookup, question answering, some FAQ tasks.
  • But MRR ignores everything after the first relevant document.

Average Precision and MAP

📐 Average Precision
\[ AP = \frac{1}{R} \sum_{k=1}^{N} P@k \cdot rel(k) \qquad MAP = \frac{1}{|Q|} \sum_{q \in Q} AP(q) \]

\(R\) is the number of relevant documents for the query and \(rel(k)\) is 1 if the document at rank \(k\) is relevant. In words: every time we meet a relevant document, record the precision at that point; then average those values over all \(R\) relevant documents. AP is for one query, MAP the mean across queries.

Worked example, R N R N R: \(P@1 = 1\), \(P@3 = 2/3\), \(P@5 = 3/5\), so \(AP = \frac{1 + 2/3 + 3/5}{3} \approx 0.756\). For rankings A and B above, AP is 1.0 and about 0.216, and RR is 1 and 0.125: the rank-aware metrics separate what P@10 could not.

Recap

MetricMain question
Precision@kHow many of the top \(k\) are relevant?
Recall@kHow much of the relevant material did we find?
RRWhere is the first relevant result?
MRRHow early is the first relevant result, on average?
APAre relevant documents consistently ranked high?
MAPMean AP across queries

So far relevance has been binary. What if some relevant documents are much better than others?

Part IV

Graded relevance: DCG and nDCG

Cranfield has graded relevance: a document may be of minimum interest, useful, highly relevant, or a complete answer. Binary metrics collapse all of these into "relevant", which loses information. This motivates DCG and nDCG.

📐 Discounted Cumulative Gain
\[ DCG@k = \sum_{i=1}^{k} \frac{2^{rel_i} - 1}{\log_2(i + 1)} \qquad nDCG@k = \frac{DCG@k}{IDCG@k} \]

Two ideas. Gain: higher grades give larger gains, \(2^{rel} - 1\): grade 0 → 0, 1 → 1, 2 → 3, 3 → 7, 4 → 15, so highly relevant documents matter more. Discount: lower ranks get less credit, dividing by \(\log_2(i + 1)\). High relevance near the top is rewarded most.

  • Why normalize? Raw DCG depends on how much relevance a query has: a query with many highly relevant documents can reach a larger DCG. So we compute the ideal ranking (highest grade first, then the next highest, …), its \(IDCG@k\), and divide. A perfect ranking has \(nDCG@k = 1\).
  • Small example: the system ranks grades [3, 0, 2, 1]; the ideal order is [3, 2, 1, 0]. The system's DCG is lower because the grade-2 and grade-1 documents appear too late.

Try it: compute nDCG

Type the grades of a ranking, top first. The tables show every term of the sum; "Sort to ideal" turns the ranking into the ideal one.

💡 Not every nDCG uses \(2^{rel} - 1\). ir_measures' default nDCG@10 (the trec_eval definition) uses the grade itself as the gain; the formula above is nDCG(dcg='exp-log2')@10. With [3, 0, 2, 1] the two give 0.951 and 0.930. Always report which one you used.

Part V

Live evaluation on Cranfield

Cranfield (ir_datasets) has graded judgments. For binary metrics we treat relevance ≥ 1 as relevant; for nDCG we keep the grades (a grade of −1 counts as 0).

qrels.py Python ▾ 
import ir_datasets
from collections import Counter

dataset = ir_datasets.load("cranfield")
queries = list(dataset.queries_iter())
qrels = list(dataset.qrels_iter())

Counter(q.relevance for q in qrels)
# Counter({3: 734, 2: 387, 4: 363, -1: 225, 1: 128})

Using ir_measures

Use an established evaluation library (ir_measures) rather than implementing every metric yourself. It reads TREC-style run files, query_id Q0 doc_id rank score system, with the top 100 results of each system for every query, made with the two search functions from Lab 04:

write_runs.py Python ▾ 
# search_tfidf and search_bm25 from Lab 04, return (doc_id, title, score)
def write_run(path, system_name, search_fn, k=100):
    with open(path, "w", encoding="utf-8") as f:
        for q in queries:
            for rank, (doc_id, title, score) in enumerate(search_fn(q.text, k=k), start=1):
                f.write(f"{q.query_id} Q0 {doc_id} {rank} {score:.8f} {system_name}\n")

write_run("lab04_tfidf.run", "tfidf", search_tfidf)
write_run("lab04_bm25.run", "bm25", search_bm25)
evaluate.py Python ▾ 
# pip install ir_measures
import ir_measures
from ir_measures import P, Recall, RR, AP, nDCG

tfidf_run = ir_measures.read_trec_run("lab04_tfidf.run")
bm25_run = ir_measures.read_trec_run("lab04_bm25.run")

metrics = [
    P(rel=1) @ 10,
    Recall(rel=1) @ 100,
    RR(rel=1),
    AP(rel=1),
    nDCG @ 10,
]

tfidf_scores = ir_measures.calc_aggregate(metrics, qrels, tfidf_run)
bm25_scores = ir_measures.calc_aggregate(metrics, qrels, bm25_run)
print(tfidf_scores)
# {AP: 0.2737..., nDCG@10: 0.3170..., RR: 0.5100..., P@10: 0.2284..., R@100: 0.7006...}
print(bm25_scores)
# {AP: 0.2405..., nDCG@10: 0.2822..., RR: 0.5044..., P@10: 0.1991..., R@100: 0.6512...}

"More sophisticated" is not automatically better; the setup matters. text.lower().split() keeps punctuation attached: 5,486 of the 12,246 distinct tokens contain it, like thickness,, which then does not match thickness. With a word tokenizer (\b\w+\b) the same BM25 reaches MAP 0.262 and P@10 0.219, closer to TF-IDF but still below it on Cranfield.

Part VI

Different metrics can disagree

  • System A has a higher P@10, system B a higher Recall@100: no contradiction, they are strong in different ways.
  • System A has a higher MRR, system B a higher MAP: this can happen, because MRR cares about the first relevant result and MAP about all of them.

Metric choice follows the task

TaskWhat mattersTypical metrics
Web searchthe early ranksP@5, P@10, nDCG@10
Legal or medical literature searchfinding as much relevant material as possibleRecall@100, Recall@1000
Navigational searchone correct result, quicklyMRR
General ad-hoc retrievalthe whole rankingMAP, nDCG

Per-query analysis

Averages can hide failures. A higher MAP for one system does not mean it wins on every query: some queries may strongly prefer one system, others the other. Serious IR evaluation combines aggregate metrics + per-query analysis + error analysis.

Part VII

Connection to RAG

A retrieval-augmented generation pipeline: question → retriever → top-k passages → LLM → answer. Suppose the correct passage is ranked 7th, but the LLM receives only the top 5: the generation model never sees the evidence. This makes \(Recall@k\) especially important for RAG retrieval.

Two different RAG failures

  • Retrieval failure: the correct evidence was not retrieved (or not within the top \(k\)).
  • Generation failure: the correct evidence was retrieved, but the model still produced a poor answer.
  • Later in the course we diagnose these two separately.

Summary: key takeaways

MetricBest interpretation
P@kHow clean are the top results?
Recall@kHow much relevant material did we retrieve?
MRRHow quickly did we find the first relevant result?
MAPAre relevant documents ranked high throughout the ranking?
nDCG@kAre the most relevant documents ranked highest?
