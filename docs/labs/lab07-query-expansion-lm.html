Query Expansion, Relevance Feedback and Language Models

Query expansion Rocchio Language models Smoothing
Work in progress These notes are still being written and reviewed: content may change, and some parts may still contain mistakes.

Overview of the lab

Up to now our retrieval systems assumed that the query already contains the right words. But users often describe the same concept differently from the documents they want: the query car repair, the relevant document automobile maintenance. This is the vocabulary mismatch problem. Two classical ways to address it: improve the query (query expansion, relevance feedback), or model how likely a document is to generate the query (language-model retrieval).

Part I

The vocabulary mismatch problem

A person immediately sees the relation between a query and a document that use different words. A purely lexical system sees only whether the strings match.

QuerycarrepairDocumentautomobilemaintenancemanual0 shared terms
QueryheartattacktreatmentDocumenttherapyformyocardialinfarction0 shared terms

TF-IDF and BM25 are powerful, but fundamentally rely on lexical evidence. They do not inherently know that car ≈ automobile, doctor ≈ physician, cheap ≈ inexpensive. For both pairs above the TF-IDF cosine and the BM25 score are exactly 0. This motivates techniques that alter or reinterpret the query.

Part II

Query expansion

📐 Query expansion

Adding terms to the original query: car repair → car automobile repair maintenance. The hope is to improve recall: a short query provides very little evidence, and expansion can retrieve documents that use different vocabulary.

  • Sources of expansion terms: thesauri, synonym dictionaries, ontologies, WordNet, user-selected relevant documents, top-ranked retrieved documents, historical query logs.
  • We focus on relevance feedback and pseudo-relevance feedback, because they connect directly to information retrieval.

Query expansion can fail: query drift

For jaguar speed, possible expansion terms are car, engine, animal, cat, wildlife. If the user meant the animal, adding vehicle-related terms creates query drift: the expansion changes the meaning of the original information need. python memory → python programming language snake reptile memory mixes unrelated senses. Query expansion is not automatically beneficial: the source and the weighting of expansion terms matter.

Part III

Relevance feedback and Rocchio

Relevance feedback uses information about which retrieved documents are relevant. It is one of the classical interactive ideas in IR.

query → retrieve documents → user marks relevant / non-relevant → modify query → retrieve again
  • Explicit relevance feedback: the user tells the system "D1 relevant, D2 not relevant, D3 relevant", and the system uses these labels to move the query toward relevant documents and away from non-relevant ones.
  • Vector-space intuition: recall the query and document vectors of Lab 04. If relevant documents cluster in one area of the vector space, move the query vector toward them; if non-relevant ones cluster elsewhere, move away from them.
📐 Rocchio algorithm
\[ \vec{q}_{new} = \alpha\,\vec{q}_{old} + \frac{\beta}{|D_r|} \sum_{d \in D_r} \vec{d} \;-\; \frac{\gamma}{|D_{nr}|} \sum_{d \in D_{nr}} \vec{d} \]

\(\vec{q}_{old}\) = original query vector; \(D_r\), \(D_{nr}\) = relevant and non-relevant documents; \(\alpha\), \(\beta\), \(\gamma\) = weights of the original query, the relevant documents and the non-relevant documents. Geometrically: start from the original query, move toward the relevant-document centroid, move away from the non-relevant centroid. This is more important than memorizing the formula.

💡 \(\alpha = 1\), \(\beta = 0.75\), \(\gamma = 0.15\) are the values suggested in Manning, Raghavan & Schütze's Introduction to Information Retrieval (§9.1.1). \(\gamma\) is usually small: relevant documents resemble each other, non-relevant documents are "all the rest" and point in many directions. Negative term weights are usually set to 0.

What does Rocchio really do?

Two things: it reweights the original query terms, and it introduces terms from the relevant documents. The resulting query can contain terms that were not present originally: that is the expansion effect. So relevance feedback is not simply "append synonyms": it changes the query representation.

Part IV

Pseudo-relevance feedback

Explicit feedback is useful, but it requires user effort. Pseudo-relevance feedback (PRF, also blind feedback) removes that requirement: the system assumes that the top-ranked documents are probably relevant and uses them as feedback automatically.

original query → initial retrieval → top-k documents → assume relevant → extract useful terms → expanded query → retrieve again
  • Example: for aircraft wing drag the top documents contain aerodynamic, airfoil, lift, flow, wing, drag; a possible expanded query is aircraft wing drag aerodynamic airfoil flow. This may retrieve relevant documents that did not contain the original wording.
  • ✅ Strength: no user interaction is required.
  • ❌ Weakness: if the initial retrieval is poor, bad top documents → bad expansion terms → an even worse query. This is another form of query drift.

prf.py Python ▾ 
# texts, bm25 (BM25Okapi on text.lower().split()), queries: as in Lab 04
import re
import numpy as np
from sklearn.feature_extraction.text import TfidfVectorizer

tfv = TfidfVectorizer(stop_words="english")
X = tfv.fit_transform(texts)
vocab = tfv.get_feature_names_out()

def expand(query, k_docs=3, n_terms=3):
    scores = bm25.get_scores(query.lower().split())
    top = scores.argsort()[::-1][:k_docs]                 # assume these are relevant
    weights = np.asarray(X[top].mean(axis=0)).ravel()     # mean TF-IDF weight of each word
    q_terms = set(re.findall(r"\b\w\w+\b", query.lower()))
    new = [vocab[j] for j in np.argsort(-weights, kind="stable") if vocab[j] not in q_terms]
    return query + " " + " ".join(new[:n_terms])

expand(queries[0].text)
# 'what similarity laws must be obeyed when constructing aeroelastic models\nof heated
#  high speed aircraft . aerothermoelastic stressing structural'

On average it helps, but query by query it helps 116 queries and hurts 92. With \(m = 2\) it hurts more queries (107) than it helps (99), although MAP still rises. Averages hide drift.

First-half recap

vocabulary mismatch → query expansion → relevance feedback → Rocchio → pseudo-relevance feedback

Instead of modifying the query, can we build a probabilistic model of the document and ask how likely it is to produce the query? That leads to language-model retrieval. First, what a language model is.

Part V

Language models

📐 Language model

A probabilistic model that assigns probabilities to terms or sequences: it predicts the probability that a sequence of tokens belongs to a language.

  • Applications: whenever there are several options and we must choose the most likely, based on the context words:
    • compare sentences to tell which are the "good" ones;
    • spell-checking (Lab 03): for "I want some cugar in my coffee", cougar or sugar?
    • automatic speech recognition: the most likely sequence of words; machine translation, question answering, summarization;
    • information retrieval: a document is likely to answer a query well if it is likely to generate the query (Part VII).
  • Language models can score and sort sentences: P(I like apples) ≫ P(I lick apples). They encode some grammaticality: P(I was going to call) ≫ P(I will going to call).

First shot: the chain rule of probability

\[ P(w_1, \ldots, w_n) = \prod_{i=1}^{n} P(w_i \mid w_1, \ldots, w_{i-1}) \]

P(I, want, some, sugar, in, my, coffee) = P(I) · P(want | I) · P(some | I, want) · … · P(coffee | I, want, some, sugar, in, my). Estimate each factor by counting in a corpus, e.g. Jane Austen's Emma (192,427 tokens in NLTK's Gutenberg collection):

chain_rule.py Python ▾ 
# import nltk; nltk.download("gutenberg")
import nltk

emma_words = list(nltk.corpus.gutenberg.words("austen-emma.txt"))
N = len(emma_words)

def count(seq):                        # how often the exact token sequence occurs
    n = len(seq)
    return sum(emma_words[i:i + n] == seq for i in range(N - n + 1))

for sentence in [["She", "was", "the", "youngest"],
                 ["I", "want", "some", "sugar", "in", "my", "coffee"]]:
    prob = count(sentence[:1]) / N                      # P(w1)
    for i in range(1, len(sentence)):
        num, den = count(sentence[:i + 1]), count(sentence[:i])
        print(f"P({sentence[i]} | {' '.join(sentence[:i])}) = {num}/{den}")
        prob *= num / den if den else 0.0
        if prob == 0: break
    print("Sentence probability:", prob)

The Markov assumption: n-grams

Take only the \(l\) words before the given one: \(P(w_1, \ldots, w_n) \approx \prod_i P(w_i \mid w_{i-l}, \ldots, w_{i-1})\).

  • Unigram model: \(P(w_i \mid w_1, \ldots, w_{i-1}) \approx P(w_i)\). P(coffee | I, want, some, sugar, in, my) ≈ P(coffee).
  • Bigram model: condition only on the previous word, \(P(w_i \mid w_{i-1})\). P(coffee | I, want, some, sugar, in, my) ≈ P(coffee | my).
  • For more context, and more dependence between words: trigram, 4-gram, … models.
📐 Maximum-likelihood estimate (bigram)
\[ P(w_i \mid w_{i-1}) = \frac{c(w_{i-1}, w_i)}{c(w_{i-1})} \]

The count of the pair divided by the count of the first word. Sentences are padded with a start symbol [s] and an end symbol [/s], so that the first word and the end of the sentence are predicted too.

1What is the downside of using a unigram model?

It ignores word order and context completely: P(I like apples) = P(apples like I), and the most probable "next word" is always the same, the most frequent word (in Emma: the comma). It cannot tell good sentences from shuffled ones.

2With the bigram model of the five sentences, what is the most probable next word for (1) [s] Sam …, (2) [s] Sam I do …, (3) [s] Sam I am Sam …, (4) [s] do I like …?

Only the last word matters. (1) after Sam: I (3/5; [/s] 2/5). (2) after do: a tie, I or like (1/2 each). (3) after Sam again: I (3/5). (4) after like: [/s] (2/3; Sam 1/3).

3Which sentence is better: (5) [s] Sam I do I like [/s], (6) [s] Sam I am [/s], (7) [s] I do like Sam I am [/s]?

(6): \(\frac35 \cdot \frac35 \cdot \frac25 \cdot \frac12 = 0.072\). (5): \(\frac35 \cdot \frac35 \cdot \frac15 \cdot \frac12 \cdot \frac25 \cdot \frac23 = 0.0096\). (7): \(\frac15 \cdot \frac15 \cdot \frac12 \cdot \frac13 \cdot \frac35 \cdot \frac25 \cdot \frac12 = 0.0008\). Longer sentences multiply more factors below 1, so raw probabilities favour short sentences; perplexity (below) normalizes by length.

A bigram model of Emma

bigram_emma.py Python ▾ 
import math, random
from collections import Counter, defaultdict
import nltk

emma_words = nltk.corpus.gutenberg.words("austen-emma.txt")
unigrams = Counter(emma_words)
bigrams = Counter(zip(emma_words, emma_words[1:]))      # exact token pairs

def p_bigram(prev, word):                                # MLE: c(prev, word) / c(prev)
    return bigrams[(prev, word)] / unigrams[prev]

sentence = ["she", "was", "to", "the"]
log_p = 0.0
for w1, w2 in zip(sentence, sentence[1:]):
    p = p_bigram(w1, w2)
    print(f"P({w2}|{w1}) = {bigrams[(w1, w2)]}/{unigrams[w1]} = {p:.4f}")
    log_p += math.log(p)                                 # add logs, do not multiply
print(f"log P = {log_p:.4f}, P = {math.exp(log_p):.3e}")
# P(was|she) = 218/1778 = 0.1226
# P(to|was) = 80/2385 = 0.0335
# P(the|to) = 236/5183 = 0.0455
# log P = -8.5830, P = 1.873e-04

following = defaultdict(Counter)
for (w1, w2), c in bigrams.items():
    following[w1][w2] = c

def generate_text(start_word, num_words=10, sample=True):
    sentence = [start_word]
    for _ in range(num_words):
        nxt = following[sentence[-1]]
        if not nxt:
            break
        words, counts = zip(*nxt.items())
        sentence.append(random.choices(words, weights=counts)[0] if sample
                        else max(nxt, key=nxt.get))
    return " ".join(sentence)

random.seed(0)
print(generate_text("I"))
print(generate_text("She"))
print(generate_text("She", sample=False))

Problem 1: underflow

Multiplying many probabilities gives very small numbers, with a risk of underflow (the product rounds to 0). Work with logarithms: \(\log(p_1 p_2 p_3 p_4) = \log p_1 + \log p_2 + \log p_3 + \log p_4\). (The notebook's cell added the probabilities themselves, \(p_1 + p_2 + \ldots\), which is not a log-probability.)

Problem 2: zero counts, even in enormous corpora

  • Google Web 1T 5-gram (2006): 1,024,908,267,229 tokens of web text, 314,843,401 distinct bigrams, and it still keeps only n-grams seen at least 40 times.
  • Shakespeare: 884,647 tokens and 29,066 word types; he produced about 300,000 bigram types out of \(29{,}066^2 \approx 844\) million possible bigrams. Most possible bigrams were never seen (99.96%).

Evaluating a language model

  • Extrinsic: with respect to some task, e.g. how often it picks the correct spelling in a spell-checking task.
  • Intrinsic: how much probability the model gives to sentences from a test corpus (which should have the same distribution of words as the training data). The Shannon game: how well do we predict the next word, given some context?
📐 Perplexity
\[ PP(W) = P(w_1, w_2, \ldots, w_n)^{-\frac{1}{n}} \]

The inverse probability of the test text, normalized by the number of words: the average number of equally likely choices the model is "perplexed" between. Minimizing perplexity is maximizing probability. For a uniform distribution, perplexity equals the size of the vocabulary: a model that generates the digits 0–5 uniformly has perplexity 6.

4With the same training data, compute the perplexity of the bigram model on the test sentence "[s] I do like Sam".

\(P = P(I \mid [s]) \cdot P(do \mid I) \cdot P(like \mid do) \cdot P(Sam \mid like) = \frac15 \cdot \frac15 \cdot \frac12 \cdot \frac13 = \frac{1}{150}\). Four words are predicted, so \(PP = 150^{1/4} \approx 3.50\). (Type the sentence into the bigram playground to check.)

Part VI

Smoothing n-gram models

We want to avoid sparse statistics, and to decide what to do when a bigram count is 0.

Add-one (Laplace) and add-\(\beta\) smoothing

\[ P_{\text{add-1}}(w_i \mid w_{i-1}) = \frac{c(w_{i-1}, w_i) + 1}{c(w_{i-1}) + |V|} \qquad P_{\text{add-}\beta}(w_i \mid w_{i-1}) = \frac{c(w_{i-1}, w_i) + \beta}{c(w_{i-1}) + \beta |V|} \]
  • Pretend we saw each word one more time than we did. This moves probability mass from "the rich" to "the poor".
  • Why is it bad? Sometimes ~90% of the probability mass is spread across unseen events, and we must know \(V\) beforehand. In the bigram playground, with Laplace the unseen pair (Sam, do) gets 1/11, as much as a seen pair gets in some rows.
5Bigram model with Laplace smoothing on the same five sentences. Give P(do|[s]), P(do|Sam), P(Sam|[s]), P(Sam|do), P(I|Sam), P(I|do), P(like|I). Then: which is more probable, (8) [s] do Sam I like or (9) [s] Sam do I like?

\(|V| = 6\): the tokens that can follow a word (I, am, Sam, do, like, [/s]). Histories: [s] 5 times, Sam 5, I 5, do 2. P(do|[s]) = (1+1)/(5+6) = 2/11; P(do|Sam) = (0+1)/11 = 1/11; P(Sam|[s]) = (3+1)/11 = 4/11; P(Sam|do) = (0+1)/(2+6) = 1/8; P(I|Sam) = (3+1)/11 = 4/11; P(I|do) = (1+1)/8 = 1/4; P(like|I) = (2+1)/11 = 3/11.

(8) = \(\frac{2}{11} \cdot \frac18 \cdot \frac{4}{11} \cdot \frac{3}{11} = \frac{3}{1331} \approx 0.00225\); (9) = \(\frac{4}{11} \cdot \frac{1}{11} \cdot \frac14 \cdot \frac{3}{11} = \frac{3}{1331}\). Equally probable. Without smoothing both would be 0 (neither "do Sam" nor "Sam do" occurs).

Good–Turing

Intuition: you are fishing and caught 10 carp, 3 perch, 2 whitefish, 1 trout, 1 salmon, 1 eel = 18 fish. How likely is it that the next species is trout? 1/18. How likely is a new species (catfish, bass)? Use the things we saw once to estimate the new things: 3/18. Then the probability of trout must be less than 1/18.

📐 Good–Turing
\[ P(\text{unseen}) = \frac{N_1}{N} \qquad c^* = \frac{(c+1)\,N_{c+1}}{N_c} \qquad P^*(x) = \frac{c^*}{N} \]

\(N_c\) = the number of n-grams (species) that occur exactly \(c\) times; \(N\) = the total count.

Try it: a Good–Turing calculator

Edit the counts. The table shows \(N_c\), the re-estimated counts and probabilities.

  • The notebook's example is the words that follow "I" in the five sentences: am 2, like 2, do 1, so \(N = 5\), \(N_1 = 1\), \(N_2 = 2\). P(unseen) = 1/5; \(c^*(do) = 2 \cdot 2 / 1 = 4\), so \(P^*(do) = 4/5\) (load After "I").
  • Problems: when a word occurs \(c\) times but no word occurs \(c+1\) times, \(c^* = 0\) (am and like above, since \(N_3 = 0\)), and with tiny data \(c^*\) can even exceed \(c\) (do: 1 → 4). Real implementations smooth the \(N_c\) values first.
  • And if \(c(\text{amazing} \mid \text{weather}) = 0\) and \(c(\text{amazing} \mid \text{trout}) = 0\), smoothing gives both unseen bigrams the same probability, although the first should be more likely, as weather is the more frequent word. So combine unigram, bigram and trigram models.

Backoff and interpolation

  • Backoff: use the trigram if you have good evidence for it, otherwise the bigram, otherwise the unigram.
  • Interpolation: always mix all three, \(P(w_i \mid w_{i-2}, w_{i-1}) = \lambda_1 P(w_i \mid w_{i-2}, w_{i-1}) + \lambda_2 P(w_i \mid w_{i-1}) + \lambda_3 P(w_i)\), with \(\lambda_1 + \lambda_2 + \lambda_3 = 1\). Estimate the \(\lambda\)s on a development set.
  • Witten–Bell smoothing: \(\lambda\) depends on the context. With \(u(h)\) = the number of different words seen after the history \(h\) and \(c(h)\) = its count: \(P_{WB}(w \mid h) = \lambda_h P_{ML}(w \mid h) + (1 - \lambda_h) P_{WB}(w \mid h')\), where \(h'\) is the shorter history and \(1 - \lambda_h = \frac{u(h)}{u(h) + c(h)}\). A history followed by many different words is more likely to be followed by a new one, so it backs off more.

💡 Corrected from the notebook: it gave the weight \(\frac{u}{u + c}\) to the higher-order model and mixed bigram and trigram notation in one formula. In Witten–Bell, \(\frac{u}{u + c}\) is the weight of the lower-order model (Chen & Goodman, An Empirical Study of Smoothing Techniques for Language Modeling, 1998).

perplexity.py (one possible solution) Python ▾ 
import math
from collections import Counter
from nltk.corpus import gutenberg

def sents(fileid):
    return [["<s>", "<s>"] + [w.lower() for w in s] + ["</s>"] for s in gutenberg.sents(fileid)]

emma = sents("austen-emma.txt")
cut = int(0.9 * len(emma))
train, test_emma = emma[:cut], emma[cut:]
tests = {"Emma (held out)": test_emma,
         "Persuasion (Austen)": sents("austen-persuasion.txt"),
         "Moby Dick (Melville)": sents("melville-moby_dick.txt")}

vocab = {w for s in train for w in s} | {"<unk>"}
unk = lambda s: [w if w in vocab else "<unk>" for w in s]
train = [unk(s) for s in train]
c1 = Counter(w for s in train for w in s[2:])
c2 = Counter(tuple(s[i-1:i+1]) for s in train for i in range(2, len(s)))
c3 = Counter(tuple(s[i-2:i+1]) for s in train for i in range(2, len(s)))
h1 = Counter(tuple(s[i-1:i]) for s in train for i in range(2, len(s)))
h2 = Counter(tuple(s[i-2:i]) for s in train for i in range(2, len(s)))
N, V = sum(c1.values()), len(vocab)

def p_uni(w): return (c1[w] + 1) / (N + V)                              # add-one
def p_bi(u, w): return (c2[(u, w)] + 1) / (h1[(u,)] + V)                 # add-one
def p_tri(t, u, w): return (c3[(t, u, w)] + 1) / (h2[(t, u)] + V)        # add-one
def p_interp(t, u, w, l=(0.6, 0.3, 0.1)):                                # MLE mixed, uni add-one
    tri = c3[(t, u, w)] / h2[(t, u)] if h2[(t, u)] else 0
    bi = c2[(u, w)] / h1[(u,)] if h1[(u,)] else 0
    return l[0] * tri + l[1] * bi + l[2] * p_uni(w)

def perplexity(test, p):
    logp, n = 0.0, 0
    for s in map(unk, test):
        for i in range(2, len(s)):
            logp += math.log(p(s[i-2], s[i-1], s[i])); n += 1
    return math.exp(-logp / n)

          "trigram, add-one": p_tri,
          "interpolated 3/2/1-gram": p_interp}
for name, test in tests.items():
    print(name, {m: round(perplexity(test, p)) for m, p in models.items()})

Part VII

Language models for retrieval: query likelihood

For classical IR we build a unigram language model for each document, and ask: how likely is this document's model to generate the query? This is the query-likelihood model.

📐 Query likelihood
\[ q = w_1, w_2, \ldots, w_n \qquad score(q, d) = P(q \mid d) = \prod_{i=1}^{n} P(w_i \mid d) \]

For document \(d\), a language model \(P(w \mid d)\) over words \(w\); the product assumes the query words are independent (a unigram model). The simplest estimate is maximum likelihood, \(P(w \mid d) = \frac{tf(w, d)}{|d|}\), with \(tf(w, d)\) the frequency of \(w\) in \(d\) and \(|d|\) the document length.

  • Interpretation: for the query wing drag, a document gets a high score if its language model gives high probability to wing and drag. Instead of "how similar are the query and document vectors?" we ask "how likely is the query under the document's term distribution?"
  • Example: the document wing wing drag flow has \(P(wing \mid d) = 2/4\), \(P(drag \mid d) = 1/4\), \(P(flow \mid d) = 1/4\). For wing drag: \(P(q \mid d) = \frac24 \cdot \frac14 = 0.125\).
Part VIII

The zero-probability problem

The document wing wing flow and the query wing drag: \(P(drag \mid d) = 0\), so \(P(q \mid d) = 0\), even if the document is otherwise highly relevant. Because probabilities are multiplied, one unseen query term makes the whole query likelihood zero. The model is too brittle: we need smoothing.

  • Smoothing intuition: even if a word does not occur in this document, give it some probability based on the collection. Combine document evidence with collection evidence.
  • Collection language model: \(P(w \mid C) = \frac{tf(w, C)}{|C|}\), with \(tf(w, C)\) the total occurrences of \(w\) in the collection and \(|C|\) its total number of tokens. Common collection terms receive some background probability.
📐 Jelinek–Mercer smoothing
\[ P(w \mid d) = (1 - \lambda)\, P_{ML}(w \mid d) + \lambda\, P(w \mid C) \]

\(\lambda\) controls how much we trust the collection: \(\lambda = 0\) uses only the document, \(\lambda = 1\) ignores the document entirely; in practice something in between. This is the interpolation of Part VI, with the collection model playing the role of the lower-order model.

Why log probabilities? Query probabilities become extremely small (\(0.01 \cdot 0.03 \cdot 0.02 \cdots\)), so, as for n-grams, score with \(\log P(q \mid d) = \sum_{w \in q} \log P(w \mid d)\): numerically more stable, and the ranking is the same.

import math
from collections import Counter

def collection_prob(term):
    return collection_counts[term] / collection_length

def query_likelihood_score(query, doc_tokens, lam=0.2):
    doc_counts = Counter(doc_tokens)
    doc_len = len(doc_tokens)
    score = 0.0
    for term in query.lower().split():
        p_doc = doc_counts[term] / doc_len if doc_len > 0 else 0.0
        p_collection = collection_prob(term)
        p = (1 - lam) * p_doc + lam * p_collection
        if p > 0:
            score += math.log(p)
        else:
            return float("-inf")
    return score

def search_ql(query, k=5):
    scored = []
    for i, tokens in enumerate(texts):
        scored.append((query_likelihood_score(query, tokens, lam=0.2), i))
    top = sorted(scored, reverse=True)[:k]
    return [(doc_ids[i], titles[i], score) for score, i in top]

def query_likelihood_score(query, doc_tokens, lam=0.2):
    doc_counts = Counter(doc_tokens)
    doc_len = len(doc_tokens)
    score = 0.0
    for term in query.lower().split():
        p_collection = collection_prob(term)
        if p_collection == 0:        # not in the collection: same for every document, skip it
            continue
        p_doc = doc_counts[term] / doc_len if doc_len > 0 else 0.0
        score += math.log((1 - lam) * p_doc + lam * p_collection)
    return score

Part XI

Bridge to dense retrieval and RAG

Classical query expansion tries to solve vocabulary mismatch by adding words (car → automobile). Dense retrieval attacks the same problem differently: instead of changing the query text, it maps both the query and the document into learned vectors (embeddings) and retrieves by semantic similarity.

classical lexical retrieval → query expansion / language models → semantic representations → dense retrieval
  • RAG systems often fail because the retriever does not find the right evidence, and vocabulary mismatch is one reason.
  • Classical methods fix it with query expansion, feedback and probabilistic term models; modern RAG systems may additionally use dense retrieval, hybrid retrieval, query rewriting, multi-query retrieval and reranking.
  • The problem is old. The tools have changed.

Summary: key takeaways

user and document use different words → query expansion → relevance feedback → pseudo-relevance feedback → language-model retrieval → smoothing → next: semantic / dense retrieval
  1. Lexical retrieval can fail because users and documents use different vocabulary.
  2. Query expansion can improve recall, but poor expansion can cause query drift.
  3. Relevance feedback moves the query toward relevant documents and away from non-relevant ones.
  4. Query-likelihood retrieval ranks documents by how likely their language models are to generate the query.
  5. Smoothing is essential, because unseen query terms otherwise produce zero probability.
