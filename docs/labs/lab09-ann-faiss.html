Lab 09

Scaling Dense Retrieval: Vector Indexes, ANN and FAISS

DPR Exact search ANN FAISS
Work in progress These notes are still being written and reviewed: content may change, and some parts may still contain mistakes.

Overview of the lab

In Lab 08 dense retrieval looked simple: encode the documents and store the vectors; encode the query, compare it against every document vector, return the nearest. That works perfectly well for 1,400 documents. But with 1 million documents? 100 million? 1 billion passages? The retrieval problem changes: the embedding model is only one part of a dense retrieval system; we also need an efficient way to search the vector collection.

dense embeddings → exact nearest-neighbor search → scaling problem → vector indexes → approximate nearest-neighbor search → latency / memory / recall trade-offs
  1. What a dense retriever contains: representation vs search.
  2. Dense Passage Retrieval: passages, training, hard negatives.
  3. Exact nearest-neighbor search and its memory cost.

  5. Approximate nearest-neighbor search: two kinds of recall, partitions and graphs.
  6. FAISS: flat and approximate indexes, IVF, HNSW.

Learning objectives

By the end you should be able to explain:

  • what dense passage retrieval is, and the difference between embedding generation and vector search;
  • why brute-force dense retrieval does not scale indefinitely, and what exact and approximate nearest-neighbor search mean;
  • why ANN deliberately trades exactness for speed, and the difference between IR relevance recall and ANN recall;
  • the basic role of FAISS, and the difference between a flat index and an approximate index;
  • the intuition behind partitioning- and graph-based ANN methods;
  • how indexing choices affect latency, memory and retrieval quality, and how vector indexes fit into a RAG pipeline.
Part I

What a dense retriever actually contains

documents → encoder → document embeddings → vector collection  |  query → encoder → query embedding → similarity search → top-k documents

There are two separate problems, and they are easily mixed together:

1. Representation

How do we map text to vectors?

SentenceTransformer, the DPR encoders, E5, BGE: representation models.

2. Search

How do we efficiently find the nearest vectors?

FAISS, HNSW, vector database indexes: search / indexing technologies.

A better embedding model does not automatically make nearest-neighbor search faster. A better index does not automatically make the embeddings semantically better.

  • Small scale: \(N = 1{,}400\) documents, \(d = 384\) dimensions. For one query, brute force computes one similarity per document: trivial.
  • Large scale: \(N = 100{,}000{,}000\) documents, \(d = 768\). Comparing the query with every vector becomes much more expensive. This motivates specialized indexing.
Part II

Dense Passage Retrieval

One influential dense-retrieval architecture: Dense Passage Retrieval (DPR) (Karpukhin et al., EMNLP 2020) uses separate encoders for questions and passages: question → question encoder → \(q\); passage → passage encoder → \(p\); then

\[ score(q, p) = q^\top p \]
  • Both encoders are BERT-base networks; the vector is the output at the [CLS] token, \(d = 768\).
  • Wikipedia is split into disjoint blocks of 100 words: 21,015,324 passages.
  • DPR beat a strong Lucene-BM25 system by 9–19 points (absolute) of top-20 passage retrieval accuracy across open-domain QA datasets.
  • Search runs on a FAISS HNSW index (Part VI): 995 questions per second, top 100 passages each, against 23.7 per second per CPU thread for BM25/Lucene, as reported in the paper.

Why passage retrieval?

A long document may contain many topics, many sections, and only one relevant paragraph. A single vector for the whole document can blur the relevant information. Take a 20-page technical report whose answer is one paragraph on page 14: if we embed the entire report, one vector must summarize everything; if we embed passages, the relevant paragraph gets its own vector. So modern retrieval often indexes passages, chunks, sections instead of whole documents, which usually gives finer retrieval granularity. This becomes critical for RAG.

passages_cranfield.py Python ▾ 
# docs, queries, model, doc_ids: as in Lab 08
import numpy as np

def passages(doc, size=100, stride=50):          # overlapping 100-word windows
    words = f"{doc.title}. {doc.text}".split()
    if len(words) <= size:
        return [" ".join(words)]
    return [" ".join(words[s:s + size]) for s in range(0, len(words) - size + stride, stride)]

passage_texts, passage_doc = [], []
for i, doc in enumerate(docs):
    for p in passages(doc):
        passage_texts.append(p)
        passage_doc.append(i)
passage_doc = np.array(passage_doc)
passage_emb = model.encode(passage_texts, batch_size=32, normalize_embeddings=True)
len(passage_texts)
# 4238

scores = query_embeddings @ passage_emb.T       # 225 x 4238
doc_scores = np.full((len(queries), len(docs)), -np.inf)
for qi in range(len(queries)):                  # a document scores as its best passage (MaxP)
    np.maximum.at(doc_scores[qi], passage_doc, scores[qi])
# evaluated like Lab 08: MAP 0.3094, nDCG@10 0.3440   (whole abstracts: 0.3207, 0.3555)

💡 On Cranfield, passages do not help: the abstracts are short (median 156 words; the model reads 256 word pieces), and a query is about the topic of the whole abstract. Splitting pays off when documents are long and the answer is local, the DPR setting of Wikipedia articles and 20-page reports.

Training intuition: positives and negatives

A dense retriever is often trained with triples (query, positive passage, negative passage). The model should make

\[ score(q, p^+) > score(q, p^-) \]

where \(p^+\) is relevant and \(p^-\) is not: the training objective pushes relevant query–passage pairs closer together. DPR's best model used the positives of the other questions in the same mini-batch as negatives ("in-batch negatives") plus one BM25 passage that matches the question but does not contain the answer.

See it: easy and hard negatives

The query symptoms of influenza and the outline's three passages, scored by all-MiniLM-L6-v2 (real cosines):

positive \(p^+\)influenza commonly causes fever, cough, and fatigue0.773
hard negativecommon symptoms of the common cold include coughing and fatigue0.599
easy negativehistory of medieval architecture0.015

The easy negative is already 0.76 below the positive: the model has nothing left to learn from it. The hard negative is only 0.17 below: it is the one that teaches the model to tell influenza from a cold. This is why negative mining matters in dense retrieval.

Part III

Exact nearest-neighbor search

Once the vectors exist, we need \(\operatorname{top-k}_{d \in D}\, sim(q, d)\). The most straightforward approach is exhaustive search:

brute_force.py Python ▾ 
# normalized vectors: inner product = cosine
scores = doc_embeddings @ query_embedding
top_k = scores.argsort()[::-1][:k]
  • Why is it exact? Every document is considered: if the highest-scoring document exists in the collection, brute force finds it. Ignoring numerical issues, there is no approximation in the search layer.
  • Cost: work proportional to \(O(Nd)\) per query: cost grows linearly with collection size.
  • Memory: dense vectors must be stored. 100 million vectors × 768 dimensions × 4 bytes (float32) = 307 GB, hundreds of gigabytes before any index overhead. A simpler board calculation: 1 million × 384 × 4 bytes ≈ 1.5 GB. Dense retrieval involves both search complexity and memory complexity: vector storage becomes a systems issue.

Try it: raw vector memory

The optional scaling calculation, \(memory = N \times d \times\) bytes per number. Production systems reduce it with float16, quantization, compressed indexes and sharding across machines.

Part IV

Why brute force becomes a problem

A service handling 10 queries per second over 100 million passage vectors (768-d) must compare every query against the whole collection: \(10 \times 10^8 \times 768 \approx 7.7 \times 10^{11}\) multiply-adds every second, streaming 307 GB of vectors through memory for each query. The result: high latency, high compute cost, large memory bandwidth, poor throughput. This motivates indexing.

The search-engine analogy: classical lexical retrieval does not scan every document either; it builds an inverted index. Dense retrieval also needs data structures that avoid unnecessary comparisons; the index is different because the objects are continuous vectors rather than discrete terms.

First-half recap

embedding model → good representation   but   100M vectors → brute force expensive → need a vector index

Must we always find the mathematically exact nearest neighbors? For many applications: not necessarily. If we can retrieve almost the same neighbors much faster, the trade-off may be worthwhile. That leads to ANN.

Part V

Approximate nearest-neighbor search

📐 Approximate nearest-neighbor (ANN) search

Find vectors that are very likely to be among the nearest neighbors without exhaustively comparing against every vector. The index may occasionally miss a true nearest neighbor; in exchange, retrieval can become much faster.

Search accuracyCost
Exact searchhighhigher
Approximate searchslightly lowermuch lower

The appropriate balance depends on the application.

Do not confuse two kinds of recall

IR recall (Lab 05)

\[ Recall@k = \frac{|\text{relevant} \cap \text{top-}k|}{|\text{relevant}|} \]

Measures relevance to the user, against human judgments.

ANN recall

\[ \text{ANN recall}@k = \frac{|E_k \cap A_k|}{k} \]

\(E_k\): the exact top \(k\); \(A_k\): the ANN top \(k\). Measures whether the index reproduces the neighbors of exact vector search. No human judgments involved.

Exact top 10 A B C D E F G H I J, ANN top 10 A B C D E F G H X Y: 8 of the exact top 10 were recovered, ANN recall@10 = 8/10 = 0.8. This does not tell us whether those documents are relevant to the user's information need.

  • Embedding failure: the relevant document has a bad vector score.
  • Index failure: a relevant, high-scoring vector exists, but the ANN search fails to retrieve it.
  • This separation of two independent failure sources is extremely useful for debugging.

Two broad ANN ideas

Many ANN methods use structures that avoid examining all vectors. Two common families: partition-based methods and graph-based methods. Both in 2-D below, on 240 invented points (distance = Euclidean, so the picture is honest).

Try it: a proximity graph (the HNSW idea)

Connect each point to its nearest neighbors. Search starts at an entry point and greedily moves to the neighbor closest to the query until no neighbor is closer: start → better neighbor → better neighbor → near the query. Click the plot to move the query.

💡 With few edges, greedy search can stop at a local minimum: a point none of whose neighbors is closer, though it is not the nearest one. HNSW (Hierarchical Navigable Small World, Malkov & Yashunin) avoids this with long-range links on sparse upper layers for quick navigation, and by keeping a list of several candidates (efSearch) instead of only the best one. More edges: better search, more memory.

Part VI

FAISS

FAISS (GitHub) is a library for efficient similarity search over dense vectors. It supports many index types; what matters here is the contrast flat exact index vs approximate index.

faiss_flat.py Python ▾ 
# pip install faiss-cpu
import faiss
import numpy as np

vectors = np.asarray(doc_embeddings, dtype="float32")    # normalized, from Lab 08
d = vectors.shape[1]

flat = faiss.IndexFlatIP(d)          # exact inner-product search
flat.add(vectors)

query_vector = model.encode([query], normalize_embeddings=True).astype("float32")
scores, ids = flat.search(query_vector, 10)   # scores and document-vector positions

❗ IndexFlatIP is still exhaustive. FAISS does not automatically mean approximate search: it can perform both, and that distinction matters.

An approximate index: IVF

An IVF (inverted file) index partitions the vectors into coarse clusters, like the regions above. At query time: query → find the promising clusters → search the vectors only inside some clusters. nlist = the number of coarse regions; nprobe = how many regions are searched. Search more regions: higher recall, higher latency; fewer: lower latency, potentially lower recall.

faiss_ivf.py Python ▾ 
query_vectors = model.encode([q.text for q in queries[:20]],
                             normalize_embeddings=True).astype("float32")
exact_scores, exact_ids = flat.search(query_vectors, 10)

nlist = 32
quantizer = faiss.IndexFlatIP(d)                     # compares the query with the 32 centroids
ivf = faiss.IndexIVFFlat(quantizer, d, nlist, faiss.METRIC_INNER_PRODUCT)
ivf.train(vectors)                                   # k-means: learn the 32 regions
ivf.add(vectors)                                     # put each vector in its region's list
ivf.nprobe = 2

ann_scores, ann_ids = ivf.search(query_vectors, 10)

def ann_recall_at_k(exact_ids, approx_ids, k=10):
    recalls = []
    for exact, approx in zip(exact_ids, approx_ids):
        recalls.append(len(set(exact[:k]) & set(approx[:k])) / k)
    return sum(recalls) / len(recalls)

print(ann_recall_at_k(exact_ids, ann_ids, k=10))
# 0.6849999999999999
  • Why training? Some vector indexes need a training step to learn their partitioning structure (here, k-means for the 32 centroids). This is different from training the embedding model: embedding-model training ≠ vector-index training.
  • HNSW at a high level: a navigable proximity graph: vectors become graph nodes, nearby vectors become connected, search traverses the graph (the widget above). It gives strong speed/recall trade-offs and is widely used in vector-search systems; in FAISS, faiss.IndexHNSWFlat(d, 32).
Part VII

Exact vs ANN on Cranfield

The Cranfield embeddings of Lab 08. Cranfield is small, so ANN is unnecessary; that is precisely why it is useful here: we can compute the exact neighbors and treat them as ground truth for the search layer.

nprobe_sweep.py Python ▾ 
import time
faiss.omp_set_num_threads(1)          # time one CPU thread

def us_per_query(index, qv, reps=200):
    t = time.perf_counter()
    for _ in range(reps):
        index.search(qv, 10)
    return (time.perf_counter() - t) / reps / len(qv) * 1e6

print(f"flat {us_per_query(flat, query_vectors):.1f} µs")
for nprobe in [1, 2, 4, 8, 16, 32]:
    ivf.nprobe = nprobe
    _, ann_ids = ivf.search(query_vectors, 10)
    print(f"{nprobe:>2}  {ann_recall_at_k(exact_ids, ann_ids):.3f}  {us_per_query(ivf, query_vectors):.1f} µs")
# flat 27.5 µs
#  1  0.530  1.8 µs          nprobe, ANN recall@10 on 20 queries, time per query
#  2  0.685  3.1 µs
#  4  0.800  5.0 µs
#  8  0.925  9.1 µs
# 16  0.990  17.5 µs
# 32  1.000  33.4 µs

Measured on a laptop (Apple M-series), one thread; the exact numbers depend on data and hardware. The pattern is the expected one: more clusters searched → higher chance of recovering the exact neighbors → higher ANN recall → more computation. And one more lesson: with all 32 lists (33.4 µs) the IVF index is slower than the flat index (27.5 µs). At 1,400 vectors an index is pure overhead.

1Does lower ANN recall always reduce nDCG?

No. From nprobe 1 to 4 it does (nDCG@10 0.3006 → 0.3506), but at nprobe = 8 the index misses 3.2% of the exact top 10 (ANN recall 0.968) and still gets nDCG@10 0.3561, higher than exact search (0.3555). Recall@10 (0.4193 vs 0.4190) and MRR (0.5494 vs 0.5482) also go up.

2Can ANN miss an exact neighbor without changing the relevance metric? Why?

Yes. A missed neighbor that is not relevant costs nothing, and the document that replaces it may even be relevant. The exact neighbors are only the nearest vectors; nearest in vector space and relevant to the user are not identical concepts. ANN recall measures the index against exact search, IR metrics measure the whole system against people.

Part VIII

Three different notions of quality

LayerQuestionMeasure
1. Embedding qualityDoes the representation rank semantically relevant documents highly?nDCG, MRR, Recall@k, MAP, against relevance judgments
2. ANN qualityDoes the approximate index recover the neighbors that exact vector search would return?ANN recall@k, relative to exact search
3. Systems qualityHow expensive is retrieval?latency, queries per second, memory, index size, build time

Related but distinct. A diagnosis table that is extremely useful later:

SymptomPossible cause
Exact dense search has poor nDCGembedding / retrieval model problem
Exact dense search is good, but ANN is worsevector-index problem
Retrieval quality is good, but too slowsystems / index configuration problem
Good dense retrieval, but a weak final answerdownstream RAG / generation problem

The recall–latency–memory trade-off

A retrieval system rarely optimizes one variable in isolation: more probes → higher recall → higher latency; more graph edges → potentially better search → more memory; compressed vectors → lower memory → possible quality loss. FAISS's HNSW on the same Cranfield vectors (32 edges per node, one thread):

faiss_hnsw.py Python ▾ 
hnsw = faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT)   # 32 edges per node
hnsw.add(vectors)                                                  # no training step; 42 ms here
all_queries = query_embeddings.astype("float32")                   # all 225
_, exact_all = flat.search(all_queries, 10)
for ef in [16, 32, 64]:
    hnsw.hnsw.efSearch = ef                # candidates kept during the graph walk
    _, ids = hnsw.search(all_queries, 10)
    print(f"{ef:>2}  {ann_recall_at_k(exact_all, ids):.4f}  {us_per_query(hnsw, all_queries, reps=50):.1f} µs")
# 16  0.9924  10.8 µs          efSearch, ANN recall@10 on 225 queries, time per query
# 32  0.9982  17.9 µs
# 64  0.9996  29.1 µs

The engineering question is not "which index is best?" but "which operating point satisfies our quality and resource requirements?"

Part IX

Connection to hybrid retrieval and RAG

Dense retrieval now has a complete architecture:

documents → chunk → embed → vector index → ANN search → top-k candidates

But Lab 08 showed that dense retrieval has weaknesses, and BM25 has different ones. This suggests hybrid retrieval: BM25 + dense retrieval → combine the candidates → rerank.

A practical RAG retriever might look like:

user question → query embedding → ANN vector search → top 50 candidates → reranking → top 5 chunks → LLM

The vector index is therefore not merely an implementation detail: it directly affects what evidence the LLM can access.

Summary: key takeaways

Lab 08: embeddings → dense similarity  |  Lab 09: scale dense similarity → exact search → ANN → vector indexes → FAISS → recall / latency / memory trade-offs
  1. The embedding model and the vector index solve different problems.
  2. Exact dense search compares against every vector; ANN avoids many comparisons.
  3. ANN deliberately trades some search accuracy for speed.
  4. ANN recall is not the same as IR Recall@k.
  5. Large-scale RAG depends on both good embeddings and good vector-search infrastructure.
