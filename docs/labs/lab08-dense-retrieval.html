Part II

Tokens and token embeddings

Neural models do not consume raw strings directly; they consume tokens. A simple tokenizer turns retrieval systems are useful into ["retrieval", "systems", "are", "useful"]. Modern language models often use subword tokens instead: a rarer word is split into pieces (conceptually retrieval → retriev + al). The exact split depends on the tokenizer.

Try it: split a text into tokens

Type a text, or pick an example. Common words stay whole; rarer words are split into pieces. A dashed chip continues the previous word.

💡 retrieval is common enough to be a single token, while embeddings is split into em + bed + ding + s. A tokenizer has a fixed vocabulary of words and word pieces; any text is written with them.

Tokens become IDs, IDs look up vectors

The tokenizer maps each token to an integer ID (for example retrieval → 26384). The model does not treat the integer itself as meaning: the integer is used to look up a vector. Each token ID maps to a learned vector, its token embedding:

\[ token_i \;\rightarrow\; e_i \in \mathbb{R}^{d} \]

See it: the lookup table

One row per vocabulary entry (tens of thousands of rows), and each row is a learned vector of hundreds of numbers; only the first few are shown. Click a token.

A token embedding is not yet contextual

The word bank has many meanings, but the tokenizer only sees the string bank. Every sentence below gets the same token ID, so it looks up the same row of the table. Click a picture.

Four different meanings, one identical starting vector. But the meaning depends on context. We need a mechanism that lets the surrounding tokens change the representation: that is the role of the Transformer.

Part III

Self-attention

What is self-attention?

Read this sentence: The animal did not cross the street because it was tired. Who is it? You know immediately that it is the animal, because you looked back at the other words. A neural model needs a way to do the same.

  • Self-attention is that mechanism: every word looks at all the other words of the same text and decides how much each one matters to it.
  • Each word updates its vector by mixing in information from the words it paid attention to.

See it: where does it look?

The shading shows how much attention it gives to each word (the weights add up to 100%). Switch the last word and watch the attention move. Illustrative numbers, chosen to show the idea.

Why do we need it?

After the lookup table (Part II) every token has a vector, but that vector knows nothing about the rest of the text. Language is full of words that only make sense in context:

  • Pronouns: it means the animal in one sentence and the street in another.
  • Ambiguous words: bank starts from the same row in river bank and bank account.
  • Small words that change everything: did not cross means the opposite of did cross.

The purpose of self-attention: turn context-free token vectors into context-aware ones.

token vectors from the lookup table → self-attention → context-aware token vectors

How it works: Query, Key, Value

Think of self-attention as retrieval inside the sentence. Each token produces three vectors:

Query (Q)

“What information am I looking for?”

Key (K)

“What kind of information do I contain / advertise?”

Value (V)

“What information should I actually give you if you attend to me?”

Query asks. Key matches. Value answers.

A real-world analogy: a library

Imagine you enter a library and ask: “I need a book about neural networks.” Your request is the query. Every book has metadata, its key; the content you read is its value.

query“I need a book about neural networks.”

Book A

keycooking, recipes, Italian

no match

Book B

keyneural networks, deep learning, AI

strong match → open it

valuethe book's actual contents

Book C

keyhistory, Rome, empire

no match

  • Query = what you are searching for.
  • Key = how each item describes itself for matching.
  • Value = the actual information you retrieve.

Where do the query, key and value come from?

Suppose the input token representations (the rows from the lookup table) are \(x_1, x_2, \dots, x_n\), stacked as the rows of \(X\). The Transformer learns three matrices \(W_Q, W_K, W_V\) and computes:

\[ Q = X\,W_Q \qquad K = X\,W_K \qquad V = X\,W_V \]

So for one token, say animal, its vector \(x\) goes through all three:

In self-attention, Q, K and V all come from the same sequence of token representations, but they are projected differently.

  • Learned and shared: the three matrices are learned in training, and every word uses the same ones.
  • Smaller: each matrix maps the long vector to a much shorter one, for example 768 numbers → 64. Comparing short vectors is cheaper, and the model runs several of these small attentions side by side, each with its own three matrices; their outputs are joined back to the full size (see multi-head attention below).

The same steps with small numbers

For one word:

  • 1. Score: compare its query with the key of every word (a dot product). A high score means a good match.

See it: the score is a dot product

The query of it is \(q = [1, 2]\). Pick a word to compare its key with the query: multiply the numbers position by position, then add. The more the key points in the same direction as the query, the higher the score.

  • 2. Weights: turn the scores into weights that add up to 1 (softmax): the better the match, the bigger the share of attention.

See it: softmax turns scores into weights

Softmax takes \(e^{\text{score}}\) for every word and divides by the total, so the weights are positive and add up to 1. Move the sliders. Try giving one word a much higher score, or raising all four scores by the same amount.

  • 3. Mix: its new vector is the weighted sum of all the values.

Try it: the three steps for it

Four words, tiny 2-number vectors (invented for the example; real ones have hundreds of numbers). Step through with ▶.

📐 Attention as learned retrieval

First, \(QK^\top\) answers: where should I look? Then \(\operatorname{softmax}\!\big(QK^\top / \sqrt{d_k}\big)\,V\) answers: what information should I retrieve from those locations? The full scaled dot-product attention:

\[ \operatorname{Attention}(Q, K, V) = \operatorname{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right) V \]

Dividing by \(\sqrt{d_k}\) (the length of the key vectors) only keeps the scores from growing too large. You do not need to derive this; understand the steps.

❗ Important caveat. Descriptions such as “animate”, “noun” or “pronoun looking for an antecedent” are conceptual explanations. In a real trained Transformer, individual dimensions of Q, K and V usually do not correspond cleanly to human-interpretable concepts: the information is stored in distributed learned representations. So do not think “dimension 3 = noun, dimension 7 = animate”; think of the vectors as learned numbers whose geometry helps the network perform useful matching and information transfer.

Multi-head attention

One attention operation, with its own \(W_Q, W_K, W_V\), is called a head. Multi-head attention runs several heads in parallel and joins their outputs back together. Conceptually, different heads can learn different kinds of relationships. For example, different heads might become sensitive to:

pronoun → antecedentverb → subjectadjective → nounnearby tokens

This is only an intuitive picture: heads are not guaranteed to correspond neatly to one linguistic relationship.

Part IV

Transformer layers

A Transformer contains repeated layers; each layer refines the representations.

token embeddings (+ positions)↓
Transformer layer 1Transformer layer 2⋮Transformer layer 6
↓contextual token representations

Inside one layer

self-attention: tokens exchange information↓ feed-forward network: each token transformed on its own

plus residual connections and normalization around both. In all-MiniLM-L6-v2: 12 heads, 384 dimensions, feed-forward width 1,536.

You do not need to derive every component. The key point: a Transformer repeatedly lets tokens interact and transforms their representations.

Position matters

A Transformer also needs information about token position. Otherwise dog bites man and man bites dog would contain the same bag of token embeddings. Different Transformer families encode position in different ways (MiniLM, like BERT, adds a learned position vector to each token embedding). For this course: token identity + position + context → contextual representation.

See it: the same words in another order

💡 The mean of the lookup embeddings is identical for both orders (cosine 1.000). The sentence embeddings do differ, thanks to positions and attention, but only a little: flights from Sofia to London and flights from London to Sofia score 0.993. For a search engine these are different requests; for this embedding model they are almost the same vector.

First-half recap

text → tokenizer → token IDs → initial token embeddings → Transformer → contextual token vectors

We now have one vector per token. How do we get one vector for an entire query or document? That is where encoders and pooling enter.

Part V

What is an encoder?

📐 Encoder
\[ \operatorname{Encoder}(text) \rightarrow \mathbb{R}^{d} \]

A model that consumes an input and returns a representation of that input. For retrieval, vector = encoder("how to repair a car"): the goal is a representation that can later be compared with document representations.

❗ Encoder does not mean generator. An encoder produces a representation (text → encoder → vector); a generative model instead repeatedly predicts output tokens.

Three broad Transformer families

ArchitectureMain roleExample familyUseful for
Encoder-onlyrepresent / understand the inputBERT (and MiniLM)classification, token labeling, retrieval embeddings, reranking components
Decoder-onlygenerate autoregressivelyGPT-style modelstext generation; the model behind RAG answers
Encoder–decodertransform one sequence into anotherT5translation, summarization, sequence-to-sequence tasks

These are broad architectural categories, not rigid task boundaries.

  • Encoder-only: input tokens → Transformer encoder → contextual representations. Every token can attend to every other token, left and right.
  • Decoder-only: predicts the next token from the previous ones, \(P(x_t \mid x_1, \ldots, x_{t-1})\). Generation is a loop: prompt → predict next token → append it → predict next token → append → … This is the conceptual model needed for RAG. A token may only attend to itself and earlier tokens (a causal mask), since the later ones do not exist yet when it is generated.
  • Encoder–decoder: input sequence → encoder → internal representations → decoder → output sequence; the decoder attends to the encoder's representations while it generates.

Part VI

From token vectors to one text vector

After a Transformer we normally have \(h_1, h_2, \ldots, h_n\): one contextual representation per token. But retrieval often wants \(E(text) \in \mathbb{R}^d\): one vector for the whole text. So we need a pooling strategy. A simple one is mean pooling, averaging the token representations:

\[ E(text) = \frac{1}{n} \sum_{i=1}^{n} h_i \]

Other strategies: the representation of a special token such as [CLS], weighted pooling, learned pooling (and max pooling, the largest value per dimension). The exact choice depends on the model: all-MiniLM-L6-v2 was trained with mean pooling followed by normalization to length 1.

See it: pooling the token vectors

The real last-layer vectors of the 8 tokens of how to repair a car engine (one row each, 384 cells, blue positive, red negative) and the pooled vector. Switch the pooling strategy to see its vector and how it ranks the five demo texts.

💡 Mean pooling reproduces model.encode exactly. With the [CLS] vector or max pooling every score lands between about 0.5 and 0.9: banana nutrition gets 0.54 for car repair, where mean pooling gives 0.05. The model was trained to make the mean useful; the other poolings are not what it learned.

The sentence embedding pipeline

text → tokenizer → token embeddings → Transformer → contextual token vectors → pooling → sentence embedding

Why not any Transformer?

A generic Transformer representation is not automatically optimized so that semantically similar sentence → nearby vector. Retrieval models are usually trained with an objective that explicitly encourages useful geometry: similar / relevant pairs move closer, irrelevant pairs move farther apart (all-MiniLM-L6-v2 was fine-tuned this way on over a billion sentence pairs). This is why a model trained for sentence embeddings or retrieval is usually preferable to taking arbitrary hidden states from a generic model.

See it: a big generic model vs a small trained one

roberta-large (355 million parameters, 24 layers, 1,024 dimensions, pre-trained only to fill in masked words), mean-pooled exactly like MiniLM, against all-MiniLM-L6-v2 (22.7 million parameters), on the five demo texts.

💡 Every roberta-large score lies between 0.988 and 0.996: all texts point in almost the same direction, and the ranking is close to noise (what should I eat to stay healthy ranks how to repair a car engine first). Size is not the point; the training objective is.

Part VII

Semantic search: what changes?

Lexical search asks

Do the query and document share useful words?

Semantic search asks

Are the query and document close in a learned representation space?

Query car repair, document automobile maintenance: a lexical system sees no term overlap; a semantic-search system can still assign high similarity (0.733 here) because the encoder maps the two texts to nearby vectors:

\[ q \rightarrow E(q) \qquad d \rightarrow E(d) \qquad score(q, d) = sim(E(q), E(d)) \]

This is not a separate magical search paradigm. It is still ranked retrieval; the main difference is the representation used to compute the score.

QuestionLexical searchSemantic search
Main signalterm overlapembedding similarity
Representationsparse term vectordense learned vector
Good at exact identifiersusually yesvariable
Good at paraphraseslimitedoften better
Needs a learned modelnoyes
Typical methodsBM25, TF-IDFbi-encoder + vector search

A useful course-level view: lexical search retrieves by words, semantic search retrieves by learned representations. Lab 10 combines both.

Part VIII

Bi-encoders

A bi-encoder encodes the query and the document independently, then compares the two vectors, for example with the cosine:

\[ score(q, d) = sim(q, d) = \cos(E(q), E(d)) \]
query↓encoder↓q vector
\(sim(q, d)\)the only point where query and document meet
document↓encoder↓d vector
  • Why bi-encoders are efficient: documents can be encoded once (documents → encoder → stored vectors). At query time only the query is encoded (query → encoder → query vector → compare with the stored vectors). This makes large-scale retrieval possible.
  • Same encoder or two encoders? Some systems use the same model for both sides (like all-MiniLM-L6-v2); others use a query encoder and a document encoder with separate parameters or roles. The core idea remains: encode independently, compare vectors.
  • ❗ Important limitation: a bi-encoder compresses each text before comparison. The query and the document never interact token by token. This is efficient, but some fine-grained relevance signals may be lost; it motivates cross-encoder reranking in Lab 10, where query and document go through the model together.

Part IX

A small embedding demo

A sentence-embedding model, all-MiniLM-L6-v2: the encoder-only Transformer of this lab (6 layers, mean pooling, 384 dimensions). All scores on this page are its real outputs, computed in Python (the model does not run in your browser).

embed.py Python ▾ 
# pip install sentence-transformers
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

texts = [
    "how to repair a car engine",
    "automobile maintenance and servicing",
    "banana nutrition and healthy diets",
    "treatment for myocardial infarction",
    "therapy after a heart attack",
]
embeddings = model.encode(texts, normalize_embeddings=True)
print(embeddings.shape)       # one row = one text embedding
# (5, 384)
print(embeddings[0][:10])     # not interpretable as words, unlike TF-IDF
# [-0.08241399  0.06654591  0.06800879 -0.03249352 -0.06150604  0.02232708
#  -0.04297901  0.01786646 -0.08514726 -0.04902695]
semantic_search.py Python ▾ 
query = "car repair"
q = model.encode([query], normalize_embeddings=True)
scores = q @ embeddings.T                 # unit vectors: dot product = cosine

for text, score in sorted(zip(texts, scores[0]), key=lambda x: x[1], reverse=True):
    print(round(float(score), 3), text)
# 0.655 how to repair a car engine
# 0.647 automobile maintenance and servicing
# 0.187 treatment for myocardial infarction
# 0.135 therapy after a heart attack
# 0.047 banana nutrition and healthy diets

Before running it: which sentence should rank highest? automobile maintenance and servicing shares no word with car repair, yet scores 0.647, almost as high as the text that contains repair and car.

What not to claim

Do not say "the model understands meaning perfectly". Embeddings can fail on negation, numbers, rare entities, specialized terminology, domain shift, long text, ambiguous queries. A learned representation is useful, not magical. Real scores for four candidate texts per query:

💡 Dense: cosine of all-MiniLM-L6-v2. BM25: rank_bm25 on the four texts only, so its IDF is crude: a word in half of the texts gets IDF 0 (why every BM25 score is 0 for the negation query). The point is not a winner: semantic retrieval is not uniformly superior, and neither is lexical.

Summary: key takeaways

  1. A token embedding is only the starting representation; a Transformer makes it contextual.
  2. Self-attention lets tokens use information from other tokens.
  3. An encoder maps text to a representation; a decoder-style LLM generates tokens autoregressively.
  4. Sentence embeddings require a way to turn contextual token vectors into one text vector.
  5. Retrieval models are trained so that vector geometry is useful for relevance or semantic similarity.
