Embeddings, Semantic Search and Dense Retrieval

Embeddings Bi-encoders Dense vs BM25 Nearest neighbors
Work in progress These notes are still being written and reviewed: content may change, and some parts may still contain mistakes.

Overview of the lab

In Lab 07 we met a major weakness of lexical retrieval: the query car repair and the document automobile maintenance share no terms, although their meanings are close. Classical IR answers with query expansion, relevance feedback and language-model retrieval. Dense retrieval takes a different approach: instead of relying mainly on exact words, it represents queries and documents as vectors in a learned semantic space.

similar meaning → nearby vectors → high similarity → high retrieval score

Part I

From lexical retrieval to semantic retrieval

car repair vs automobile maintenance; heart attack treatment vs therapy for myocardial infarction. A lexical system sees limited overlap; a human sees semantic similarity. The question becomes: can we represent text in a way that places semantically related texts close together? That is the motivation for embeddings.

  • Sparse representations: TF-IDF represents a document as a vector over the vocabulary terms. With 50,000 terms the vector looks like \([0, 0, 0.3, 0, \ldots, 1.2, \ldots, 0]\): most dimensions are zero, and each dimension corresponds to a term.
  • Dense representations: an embedding looks like \([0.12, -0.43, 0.08, 0.71, \ldots]\): most dimensions are non-zero, and they do not correspond to human-readable terms. They are learned features.

Part II

What is an embedding?

📐 Embedding
\[ E(x) \in \mathbb{R}^d \qquad E(\text{“car repair”}) = [0.14, -0.31, \ldots, 0.62] \]

A vector representation of \(x\), which may be a word, sentence, query, passage or document; \(d\) is the embedding dimension. The goal: semantically related text obtains similar vectors.

  • Geometric intuition: if car repair, automobile maintenance and car engine service get embeddings close together, while banana nutrition and medieval history appear elsewhere, then retrieval becomes a geometric search problem.
  • ❗ Embeddings are not a dictionary of synonyms. They encode distributed statistical information learned from data. Depending on how the model was trained, they may capture semantic similarity, paraphrase similarity, topic similarity, syntactic patterns, domain-specific associations.
  • A simple analogy: lexical retrieval asks "do the same words occur?"; dense retrieval asks "are these texts represented nearby in the learned vector space?" A simplification, but a useful one.

Part III

From embeddings to retrieval

A dense retriever needs two functions, encode query and encode document, and a similarity:

\[ \vec{q} = E_q(q) \qquad \vec{d} = E_d(d) \qquad score(q, d) = sim(\vec{q}, \vec{d}) \]

The bi-encoder

query↓query encoder \(E_q\)↓query vector \(\vec q\)
\(sim(\vec q, \vec d)\)the only point where query and document meet
document↓document encoder \(E_d\)↓document vector \(\vec d\)

The query and the document are encoded separately. That is the key efficiency advantage: documents can be encoded in advance (documents → encoder → stored embeddings), and at query time only the new query is encoded and compared with the stored vectors. This avoids running a large model jointly over every query–document pair, as a cross-encoder does (query and document go through the model together; more accurate, far more expensive, later used for reranking).

WorkWhen
Offlineencode 1 million documents, store the vectors, build a vector indexonce
Onlineencode the query, search the index, return the top \(k\)for every query

This pattern appears directly in RAG systems. One encoder or two? The same encoder for queries and documents (as with all-MiniLM-L6-v2 below), or different query and document encoders; the idea is the same: map both into a compatible vector space.

Part IV

Similarity functions

Once the query and the document are vectors, we need a score. Common choices: cosine similarity, dot product, Euclidean distance.

📐 Three similarity functions
\[ \cos(q, d) = \frac{q \cdot d}{\|q\|\,\|d\|} \qquad score(q, d) = q^\top d \qquad \|q - d\|_2 \ \text{(smaller = closer)} \]

Cosine is the same geometric idea as with TF-IDF vectors in Lab 04; what differs is the representation (hand-designed lexical dimensions vs learned embedding dimensions). If the embeddings are normalized to unit length, \(q^\top d = \cos(q, d)\), and also \(\|q - d\|^2 = 2 - 2\cos(q, d)\): all three give the same ranking.

  • Why normalization matters: if vector A has a large magnitude and B a small one, a raw dot product can be influenced by vector length. Cosine removes that magnitude effect. Whether normalization is appropriate depends on the embedding model.
  • ❗ In practice, the similarity function should match how the model was trained.

Try it: when the three disagree

A query \(q\) and three documents in 2-D (invented). Stretch document A without turning it: its cosine does not change, but its dot product grows and its distance changes. Tick "normalize" to put every vector on the unit circle.

First-half recap

text → encoder → embedding vector → similarity function → ranking

BM25: term overlap drives the score. Dense retrieval: embedding similarity drives the score. Let us now see what these vectors actually look like.

Part V

A live embedding demo

A small Sentence Transformers model, all-MiniLM-L6-v2: 6 layers, 384-dimensional embeddings, fine-tuned on over a billion sentence pairs; text longer than 256 word pieces is truncated. All scores on this page are its real outputs, computed in Python (the model does not run in your browser).

embed.py Python ▾ 
# pip install sentence-transformers
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

texts = [
    "how to repair a car engine",
    "automobile maintenance and servicing",
    "banana nutrition and healthy diets",
    "treatment for myocardial infarction",
    "therapy after a heart attack",
]
embeddings = model.encode(texts, normalize_embeddings=True)
print(embeddings.shape)       # rows = texts, columns = embedding dimensions
# (5, 384)
print(embeddings[0][:10])     # not interpretable as words, unlike TF-IDF
# [-0.08241399  0.06654591  0.06800879 -0.03249352 -0.06150604  0.02232708
#  -0.04297901  0.01786646 -0.08514726 -0.04902695]
semantic_search.py Python ▾ 
query = "car repair"
q = model.encode([query], normalize_embeddings=True)
scores = q @ embeddings.T                 # unit vectors: dot product = cosine

for text, score in sorted(zip(texts, scores[0]), key=lambda x: x[1], reverse=True):
    print(round(float(score), 3), text)
# 0.655 how to repair a car engine
# 0.647 automobile maintenance and servicing
# 0.187 treatment for myocardial infarction
# 0.135 therapy after a heart attack
# 0.047 banana nutrition and healthy diets

Before running it: which text do you expect to rank highest? automobile maintenance and servicing shares no word with car repair, yet scores 0.647, almost as high as the text that contains repair and car. That is the semantic-search moment. For heart attack treatment: therapy after a heart attack 0.851, treatment for myocardial infarction 0.672, everything else below 0.14.

Important caution

Do not conclude that dense retrieval understands meaning perfectly: that is false. Embeddings can fail because of domain mismatch, negation, rare entities, numbers, dates, exact identifiers, specialized terminology, long documents, ambiguous queries. Dense retrieval solves some lexical mismatch problems, not all retrieval problems (Part VII shows real failures).

Part VI

Dense retrieval on Cranfield

The Cranfield collection again, so that the retrieval methods stay comparable across labs.

encode_cranfield.py Python ▾ 
# pip install sentence-transformers ir_datasets numpy
import ir_datasets

dataset = ir_datasets.load("cranfield")
docs = list(dataset.docs_iter())
queries = list(dataset.queries_iter())

doc_ids = [doc.doc_id for doc in docs]
titles = [doc.title for doc in docs]
texts = [f"{doc.title}. {doc.text}" for doc in docs]

doc_embeddings = model.encode(texts, batch_size=32, normalize_embeddings=True,
                              show_progress_bar=True)       # the expensive offline step
doc_embeddings.shape
# (1400, 384)
search_dense.py Python ▾ 
import numpy as np

def search_dense(query, k=5):
    q = model.encode([query], normalize_embeddings=True)[0]
    scores = doc_embeddings @ q           # one dot product per document
    top = np.argsort(scores)[::-1][:k]
    return [(doc_ids[i], titles[i], float(scores[i])) for i in top]

q = queries[0].text
print(q)
for result in search_dense(q):
    print(result)
# what similarity laws must be obeyed when constructing aeroelastic models
# of heated high speed aircraft .
# ('486', 'similarity laws for aerothermoelastic testing .', 0.718813419342041)
# ('184', 'scale models for thermo-aeroelastic research .', 0.6493932008743286)
# ('13', 'similarity laws for stressing heated wings .', 0.6335977911949158)

  • Cost: encoding the 1,400 abstracts took 4.5 seconds here on a laptop. For a large collection, the document vectors are computed once, stored and indexed.
  • ❗ Truncation: 418 of the 1,400 abstracts (30%) are longer than the model's 256 word pieces (the longest has 808). Everything after the limit is silently ignored: the "long documents" failure of the caution above. Real systems split long documents into passages (chunks).

Part VII

Dense retrieval vs BM25

BM25 is strong when

  • exact words matter
  • rare entities and identifiers matter
  • technical terminology overlaps
  • queries contain distinctive lexical clues

"RFC 9309", "BM25 k1 parameter", "Python TypeError", "COVID-19 B.1.1.529"

Dense retrieval is useful when

  • meaning overlaps
  • wording differs
  • queries are paraphrases
  • documents use related terminology

car repair / automobile maintenance; heart attack treatment / therapy for myocardial infarction

Dense retrieval can fail too

A semantic model may strongly associate documents NOT about neural networks with neural networks despite the negation; for error code 0x80070005, exact lexical matching may be much more reliable than semantic similarity. The real scores, for four candidate texts per query:

💡 Dense: cosine of all-MiniLM-L6-v2. BM25: rank_bm25 on the four texts only, so its IDF is crude: a word in half of the texts gets IDF 0 (why every BM25 score is 0 for the negation query). The point is not a winner: semantic retrieval is not uniformly superior, and neither is lexical.

Key teaching point

Not BM25 → obsolete → dense retrieval, but lexical retrieval + dense retrieval + reranking: different signals are useful for different failure modes.

Do not declare a winner by inspection: evaluate

If BM25 and dense retrieval produce different rankings, which one is better? The answer is still: evaluate them, with the methodology of Lab 05. The evaluation framework survives even when the retrieval model changes.

💡 Computed in your browser from the runs (top 100 per query); identical to ir_measures. On Cranfield the dense model wins on every measure, although it was never trained on aeronautics and truncates 30% of the abstracts. But it wins on average: per query it is better on 152 queries, worse on 67. Collections of short, technical, keyword-like queries can go the other way; measure on yours.

evaluate_dense.py Python ▾ 
import ir_measures
from ir_measures import P, Recall, RR, AP, nDCG

qrels = list(dataset.qrels_iter())
query_embeddings = model.encode([q.text for q in queries], normalize_embeddings=True)
scores = query_embeddings @ doc_embeddings.T                 # 225 x 1400

run = []
for qi, q in enumerate(queries):
    for i in np.argsort(-scores[qi], kind="stable")[:100]:
        run.append(ir_measures.ScoredDoc(q.query_id, doc_ids[i], float(scores[qi][i])))

ir_measures.calc_aggregate([P(rel=1)@10, Recall(rel=1)@10, Recall(rel=1)@100,
                            RR(rel=1), AP(rel=1), nDCG@10], qrels, run)
# {P@10: 0.2480, R@10: 0.4190, R@100: 0.7783, RR: 0.5482, AP: 0.3207, nDCG@10: 0.3555}

Part VIII

Nearest-neighbor search

The demo computes the query vector against every document vector: exact search. With 1,400 documents that is easy; with 100 million it becomes expensive.

📐 Nearest-neighbor search
\[ \operatorname{topk}_{d \in D}\; sim(q, d) \]

Given one query vector, find the closest document vectors. For small collections brute force is fine; for large collections we usually use an index.

Try it: the cost of brute force

One query against \(N\) stored vectors of dimension \(d\): \(N \cdot d\) multiply-adds, and the vectors must be in memory (4 bytes per number). The time assumes \(10^{10}\) multiply-adds per second, a rough order of magnitude for one fast CPU.

  • Approximate nearest neighbors (ANN) trade some exactness for speed: do not compare against every vector; organize the vector space so that promising candidates can be found quickly. Common systems: FAISS, HNSW-based indexes, vector databases.
  • Quality vs latency: a new engineering trade-off, more accurate search ↔ more computation. The nearest-neighbor layer has its own recall: did the ANN index find the same good candidates that exact search would have found? This is separate from semantic relevance.
  • The algorithms are the topic of Lab 09; the point today is architectural.
Part IX

Connection to RAG

Dense retrieval is one of the standard building blocks of RAG:

documents → chunk → embed → vector index  |  user query → embed → nearest-neighbor search → top-k chunks → LLM

This is why dense retrieval must be understood before RAG frameworks: the framework is not the retrieval concept. And the classic failure mode applies: if the answer is in chunk D17, dense retrieval ranks it 12th, and the LLM receives the top 5, the generation model never sees the evidence. The retrieval problem comes first.

Summary: key takeaways

lexical retrieval (TF-IDF / BM25) → vocabulary mismatch → query expansion / LM retrieval → embeddings → dense retrieval → nearest-neighbor search → RAG retrieval
  1. Embeddings represent text as dense learned vectors.
  2. Dense retrieval ranks documents by similarity in embedding space.
  3. Bi-encoders are efficient because documents can be encoded offline.
  4. Dense retrieval helps with semantic mismatch, but does not replace lexical retrieval in every setting.
  5. Dense retrieval is one of the core retrieval mechanisms used in RAG systems.
